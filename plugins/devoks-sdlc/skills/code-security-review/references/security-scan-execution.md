# security-scan-execution — 보안 검증 실행 절차 (엔진 SSOT)

**호출 주체:** `code-security-reviewer` 에이전트 (subagent 안에서 실행).
진입 스킬(`devoks-sdlc:code-security-review`)의 Phase 0에서 `scope`가 이미 확정된 상태를 전제한다 —
이 문서 안에서 범위 모호성을 다시 확인하지 않는다.

리포트 출력 형식은 `report-template.md`(같은 디렉토리)가 SSOT다.

---

## 입력 파라미터

| 파라미터 | 타입 | 설명 |
|---------|------|------|
| `scope` | 경로 (전체 repo면 `.`) | 호출자가 이미 확정한 검증 대상 |
| `focus` | 선택 | 중점 카테고리(의존성 / 시크릿 / 인증인가 / 입력검증 / 설정, 조건부: 업로드 / 파일작업 / 남용 / PII / LLM) |
| 제외 범위 | 선택 | 벤더 디렉토리, 생성물 등 |

---

## 1. 스캔 범위·스택 감지

- 전체 repo 또는 지정 scope를 확정한다.
- 패키지 매니저·언어·프레임워크를 먼저 감지한다(`package.json`/lockfile/설정파일).
- audit·grep 등 명령은 출력을 파일로 리다이렉트해 실행하고(`<명령> > "$OUT" 2>&1; echo "exit=$?"`), 거기서 **필요한 줄만 추출**한다(대용량 출력 격리 — 원문 전체 Read 금지).

## 2. 프로젝트 고유 정책 감지 (있으면 우선)

- 프로젝트 active convention `.claude/rules/project-convention.md`의 Security 섹션, `.claude/refs/code-review.md`의 보안 항목, `.claude/refs/`의 스택 한정 보안 ref(`*-security.md` — 탐지 시그널 표가 있으면 grep 패턴으로 그대로 쓴다), `.claude/CLAUDE.md`가 선언한 민감 파일/시크릿 정책이 **존재하면 우선 적용**한다.
- 없으면 범용 기준만 적용한다.
- 이 문서나 SKILL.md에 특정 식별자·파일명을 박지 않는다 — 감지값이 SSOT다.

## 3. 신뢰 경계 매핑 (점검 전 1회)

카테고리를 순회하기 전에 scope의 **신뢰 경계**를 먼저 적는다. 아래 카테고리 점검은 이 지도 위에서 "어느 입력이 어느 싱크에 닿는가"를 따라가는 작업이다.

- **진입점** — 외부 요청을 받는 곳(HTTP 라우트·핸들러, 메시지 컨슈머, CLI 인자, 웹훅, 클라이언트라면 URL·폼·`postMessage`).
- **신뢰할 수 없는 입력원** — 사용자 입력, 업로드 파일, 서드파티 응답, LLM 출력.
- **권한 경계** — 인증이 확정되는 지점, 권한이 갈리는 지점(일반/관리자, 테넌트), 비밀값이 쓰이는 지점.
- **위험한 싱크** — 쿼리·명령 실행, 파일시스템 경로, HTML 렌더, 외부 요청(SSRF), 로그·외부 전송.

리포트 `📋 검증 대상`의 `신뢰 경계`에 3~6줄로 요약한다. 경계가 너무 많으면 고위험 경계(인증·결제·데이터 변경·외부 전송)만 적고 그렇다고 밝힌다.

## 4. 점검 실행

아래 카테고리를 순회하며 증거 기반으로 점검한다(추측 금지). 의심 지점은 코드 흐름을 따라 **실제 도달 가능성**을 확인한다.
`focus`가 지정됐으면 그 카테고리를 먼저·깊게 보되, 나머지 카테고리도 생략하지 않는다.

**기본 카테고리 (항상):**
- **의존성 취약점** — 프로젝트 패키지 매니저를 감지해 해당 audit 실행(`npm/pnpm/yarn audit`, `pip-audit` 등). lockfile이 있으면 커밋 여부, manifest의 git/http URL 의존성, install script 정책도 확인한다.
- **시크릿 하드코딩** — API 키·토큰·private key·연결문자열 등 범용 패턴 전수 스캔.
- **인증·인가 경계 우회** — 보호 경로가 일관되게 가드되는지 흐름 분석(프로젝트의 가드 패턴을 먼저 식별, 특정 함수명 가정 금지). 인가 판단에 클라이언트가 보낸 식별자(userId·role)를 그대로 쓰는지(IDOR) 함께 본다.
- **입력 검증 위협** — 인젝션 / XSS / SSRF 등.
- **민감 데이터 노출 · 안전하지 않은 설정** — 민감값 로깅, CORS·암호화·기본 크리덴셜 등.

**조건부 카테고리 — 1단계 스택 감지·3단계 신뢰 경계에서 해당 코드가 확인될 때만 점검한다.** 해당 코드가 없으면 리포트에 `해당 없음`으로 남기고 넘어간다(점검했다고 쓰지 않는다).

| 카테고리 | 발동 신호 | 확인할 것 |
|---|---|---|
| 파일 업로드 | multipart 처리, 업로드 핸들러, 스토리지 SDK 쓰기 | 서버 측 타입(내용 기반)·크기·개수 제한, 저장 경로를 사용자 파일명으로 조합하지 않음, 업로드물이 앱 origin에서 인라인 렌더되지 않음(SVG·HTML) |
| 파괴적 파일 작업 | 사용자 입력·외부 값으로 조합한 경로에 대한 삭제·덮어쓰기·이동, 압축 해제 | 경로 정규화 후 허용 루트 이탈 차단(path traversal, zip slip), 삭제 대상 화이트리스트 |
| 무차별 대입·남용 | 로그인·OTP·비밀번호 재설정·비싼 연산·외부 과금 API 엔드포인트 | rate limiting·계정 잠금·쿼터가 서버에 있는지 |
| 개인정보(PII) | 이메일·전화·주소·결제·식별번호 필드 처리, 분석·리플레이·에러 트래킹 SDK | 로그·외부 전송 payload의 PII 포함 여부, 필요 이상 수집·응답 과다 노출, 마스킹 |
| AI/LLM 기능 | LLM SDK·엔드포인트 호출, 프롬프트 조립, 모델 tool/function calling | 모델 출력을 신뢰 입력으로 쓰지 않음(렌더 sanitize·쿼리/명령/URL 조합 금지), 시스템 프롬프트에 비밀·권한 규칙 없음, 모델이 트리거하는 동작의 서버 재인가, 공급자 키가 클라이언트에 없음, 토큰·요청 상한(OWASP LLM Top 10 2025 기준) |

## 5. 리포트

`report-template.md`의 템플릿으로 출력한다. 이모지를 그대로 포함한다.
심각도 분류는 `.claude/refs/code-review.md §8`을 따른다.

## 완료 기준

- 신뢰 경계 요약이 채워져 있고, 조건부 카테고리는 각각 점검 결과 또는 `해당 없음`으로 표시돼 있다.
- 취약점 0이면 "통과"를 명시적으로 선언한다.
- 발견 시 심각도별 집계 + 위치 + 재현/검증 방법 + 권장 조치 + 후속 테스트 필요 여부 + 즉시/후속 액션이 채워져 있다.
- 코드 수정은 제안만 하고, 적용은 사용자 승인 후.
