# feature-intent-interview — 기능 의도 인터뷰 (Define 앞단)

사람이 요청하는 것("대시보드 만들어줘")과 실제로 원하는 것("실험 목록이 없다")은 자주 다르다. 그 차이는
FRD·PLAN·코드가 생기기 **전**에 찾는 것이 가장 싸다. 이 스킬은 질문을 하나씩 던져 의도를 좁히고, 사용자가
명시적으로 승인한 **Intent**를 FRD 정련의 입력으로 넘긴다. FRD를 직접 쓰지 않는다(FRD 작성 SSOT는
`devoks-sdlc:feature-frd-author`).

## 범위 (중요)

| 입력 상태 | 쓸 스킬 |
|---|---|
| **의도가 불명확** — User·Why now·Success·Out of scope 중 하나라도 추측해야 채울 수 있음 | **이 스킬** |
| 의도는 있으나 **방향이 여러 갈래** — 무엇을 만들지 선택지를 넓혀 보고 좁혀야 함 | `devoks-sdlc:feature-idea-refine` |
| 방향이 정해졌고 **초안이 있음** — 요구를 EARS·Contract·Edge로 정형화 | `devoks-sdlc:feature-frd-author` |

- 이름 바꾸기·오타·명확한 버그 수정처럼 의도가 자명한 요청, 정보 질문("X는 어떻게 동작해?")에는 쓰지 않는다.
- **HITL 전용** — 질문에 바로 답할 사용자가 있어야 한다. 질문이 사용자에게 전달되지 않는 맥락(작업을 위임받은 서브에이전트, `/loop`, 스케줄 실행,
  자동 파이프라인)에서는 실행하지 않고 "의도 불명확 — 사용자 확인 필요"를 blocker로 보고한다(추측으로 채우지 않는다).

## 호출 방법

```
/devoks-sdlc:feature-intent-interview [ask=<요청 본문> (default: 대화 맥락)] [out=<디렉터리> (default: 워크스페이스)]
```

> 표기: `key=값` 필수 · `[key=값]` 선택 · `(default: X)` 미지정 시 X로 진행.

- `out` 기본값과 `FRD.draft.md` 기록 형식은 `../feature-workflow-runner/references/output-location.md`가 SSOT다.

## 절차

### 1. 가설과 확신도부터

질문 전에 현재 이해를 **한 문장 가설**과 **확신도(%)**로 적는다. 70% 미만이면 같은 줄에 무엇이 비었는지 붙인다.

```
가설: 스탠드업에서 "요즘 어때?"에 답할 방법을 원하고, "대시보드"는 떠오른 관습적 답이다.
확신도: ~30% — 누구를 위한 것인지, "지표"가 무엇인지, 성공 모습이 비어 있음
```

확신도는 정직해야 한다. 다음 질문 3개에 대한 사용자 반응을 예측할 수 없다면 숫자가 높을 수 없다.

### 2. 질문은 한 번에 하나, 예상 답을 붙여서

```
Q: <초점이 하나인 질문>
예상: <내 가설 답과 그렇게 본 이유>
```

- 한 메시지에 질문 1개. 답을 받은 뒤 다음 질문을 정한다 — 세 번째 질문은 첫 답에 따라 달라지는 경우가 많다.
- 일반 텍스트 턴으로 묻는다(AskUserQuestion 금지 — 선택지가 답의 범위를 미리 좁힌다). 단, 사용자가 "알아서 해"로 결정을 넘길 때만 구체 선택지 2개를 제시한다.
- 예상 답은 반박당할 각오로 붙인다. 사용자가 맞장구만 치는 것 같으면 일부러 반대 방향 예상을 던져 본다.
- 매 답 뒤에 갱신된 가설·확신도를 한 줄로 보여준다.

### 3. "원하는 것" vs "원해야 할 것 같은 것"

다음 신호가 보이면 모범답안을 말하고 있을 가능성이 크다.

- 구체 없는 모범 용어("확장 가능하게", "깔끔한 구조", "모던하게")가 목표 자리에 옴
- 관습에 기댐("보통 앱들처럼", "표준 방식으로"), "~해야 할 것 같아요"
- 그때 묻는다: **"누구에게도 설명할 필요가 없다면, 실제로 뭘 원하세요?"**

### 4. 멈춤 조건

**다음 질문 3개에 대한 사용자 반응을 예측할 수 있으면** 멈추고 5단계로 간다. 몇 차례 물었는데도 확신도가
오르지 않으면 질문이 틀린 것이다 — "N개를 물었는데도 반응을 예측하지 못하겠어요. 근본적인 무언가가 빠진 것
같은데 한 발 물러나 볼까요?"라고 말하고 프레임을 바꾼다.

### 5. 사용자의 말로 다시 정리

```
지금 제가 이해한 내용입니다:
- Outcome:      <한 줄 — 무엇이 달라지는가>
- User:         <한 줄 — 누가 혜택을 받는가>
- Why now:      <한 줄 — 왜 지금인가>
- Success:      <한 줄 — 어떻게 됐다고 판단하는가, 가능하면 측정값>
- Constraint:   <한 줄 — 넘을 수 없는 제약>
- Out of scope: <한 줄 이상 — 이번에 하지 않을 것>

맞나요 / 아니면 / 고칠 부분?
```

**Out of scope는 생략 불가** — 어긋남의 절반은 "만들지 않을 것"에 대한 말 없는 불일치다.

### 6. 명시적 승인

- 통과는 정리 내용을 그대로 받아들인다는 명시 표현("네"·"맞아요"·"동의해요, 기록해 주세요" 등)뿐이다. "알아서 해주세요"는 결정 위임이므로 구체 선택지 2개로 다시 묻고,
  "좋아요"·"그렇게 가죠"는 "고칠 부분 없을까요?"로 한 번 더 확인한다.
- 수정이 오면 반영해 5단계를 다시 보여준다.

### 7. 기록하고 멈춤

승인되면:

1. 워크스페이스를 확정한다(`output-location.md` — feature-name을 정해 1회 확인, 이미 있으면 이어 쓴다. 사용자가 `out`이나 경로를 이미 지정했으면 확인 없이 그 경로를 쓴다).
2. `<out>/FRD.draft.md`에 기록한다. **덮어쓰지 않는다.**
   - 파일이 없으면 출처 헤더(`feature-intent-interview`, 날짜) + 원래 요청 원문 verbatim + 아래 섹션으로 만든다.
   - 파일이 있으면(다른 스킬·초안이 먼저 만든 경우) 맨 아래에 아래 섹션만 추가한다.

   ```markdown
   ## 확정 결정 — feature-intent-interview (<yyyy-MM-dd>)
   - Outcome: …
   - User: …
   - Why now: …
   - Success: …
   - Constraint: …
   - Out of scope: …
   - 남은 질문: <인터뷰 중 답이 보류된 것, 없으면 "없음">
   ```

3. 다음 경로를 제안하고 **턴을 끝낸다** — 같은 턴에 FRD 작성·아이디어 확장을 시작하지 않는다.
   - 방향이 하나로 정해졌으면 → `/devoks-sdlc:feature-frd-author frd=<out>/FRD.draft.md`
   - "원하는 건 알겠는데 어떻게 만들지 갈래가 많다"면 → `/devoks-sdlc:feature-idea-refine`

## 완료 기준

- 첫 턴에 가설 + 확신도가 있었고, 70% 미만 확신도에는 이유가 붙었다.
- 질문이 한 번에 하나씩, 예상 답과 함께 나갔다.
- 모범답안 신호가 나왔으면 "실제로 뭘 원하세요?" 탐침을 최소 1회 했다.
- 6줄 정리(Out of scope 포함)를 사용자가 명시적으로 승인했다.
- `FRD.draft.md`에 확정 결정 섹션이 기록됐고 기존 내용은 보존됐다.
- 승인 직후 턴을 끝냈다.
