# feature-interview — 기능 의도·방향 정련 (FRD 앞단)

사람이 요청하는 것("대시보드 만들어줘")과 실제로 원하는 것("실험 목록이 없다")은 자주 다르고, 막연한
아이디어를 바로 FRD로 옮기면 처음 떠오른 형태가 그대로 굳는다. 이 스킬은 FRD를 쓰기 **전**에 대화로
의도와 방향을 좁히고, 그 과정에서 모인 답·결정을 **정련 요약** 하나로 만들어 `devoks-sdlc:feature-frd-author`에
그대로 넘긴다. 파일을 따로 만들지 않는다 — 요약은 frd-author의 "대화로 받은 초안"이 되고, frd-author가
`FRD.draft.md`로 보존한다. FRD 작성 SSOT는 frd-author다.

## 범위 (중요)

| 입력 상태 | 쓸 스킬 |
|---|---|
| 원하는 것이 불명확하거나 방향이 여러 갈래 | **이 스킬** → 승인 후 frd-author 자동 연결 |
| 방향이 정해졌고 초안이 있음 | `devoks-sdlc:feature-frd-author` (의도 공백을 발견하면 Phase 0에서 이 스킬로 진입) |
| 기능 하나가 아니라 제품·장기 프로젝트 전체 | `devoks-sdlc:product-prd-author` (PRD + 기능 백로그 — 백로그 항목의 FRD 시드로 내려온다) |

- 이름 바꾸기·오타·명확한 버그 수정처럼 의도가 자명한 요청, 정보 질문에는 쓰지 않는다.
- **HITL 전용** — 질문이 사용자에게 전달되지 않는 맥락(위임받은 서브에이전트, `/loop`, 스케줄 실행, 자동
  파이프라인)에서는 실행하지 않고 "의도 불명확 — 사용자 확인 필요"를 blocker로 보고한다(추측으로 채우지 않는다).
- 하지 않는 것: 요구의 EARS 정형화·Contract·Edge·기술 설계(frd-author), 작업 분해, 코드 작성.

## 호출 방법

```
/devoks-sdlc:feature-interview [ask=<요청·아이디어 본문> (default: 대화 맥락)] [out=<디렉터리> (default: 워크스페이스)]
```

> 표기: `key=값` 필수 · `[key=값]` 선택 · `(default: X)` 미지정 시 X로 진행.

- `out`은 frd-author로 그대로 넘긴다(워크스페이스 규칙 SSOT: `../feature-workflow-runner/references/output-location.md`).

## 절차

### 1. 가설과 확신도부터

질문 전에 현재 이해를 **한 문장 가설**과 **확신도(%)**로 적는다. 70% 미만이면 같은 줄에 무엇이 비었는지 붙인다.

```
가설: 스탠드업에서 "요즘 어때?"에 답할 방법을 원하고, "대시보드"는 떠오른 관습적 답이다.
확신도: ~30% — 누구를 위한 것인지, "지표"가 무엇인지, 성공 모습이 비어 있음
```

확신도는 정직해야 한다 — 다음 질문 3개에 대한 사용자 반응을 예측할 수 없다면 숫자가 높을 수 없다.
코드베이스 안이면 관련 기존 화면·모듈·데이터 모델을 먼저 훑어 가설과 질문의 근거로 쓴다(파일 경로 인용).

### 2. 지금 빈 것이 무엇인지로 진행 방식을 고른다

한 대화 안에서 두 방식을 오가도 된다. 매 답 뒤에 갱신된 가설·확신도를 한 줄로 보여준다.

**의도가 비었을 때 — 질문은 한 번에 하나, 예상 답을 붙여서**

```
Q: <초점이 하나인 질문>
예상: <내 가설 답과 그렇게 본 이유>
```

- 한 메시지에 질문 1개. 세 번째 질문은 첫 답에 따라 달라지는 경우가 많다.
- 일반 텍스트로 묻는다(AskUserQuestion 금지 — 선택지가 답의 범위를 미리 좁힌다). 사용자가 "알아서 해"로 결정을 넘길 때만 구체 선택지 2개를 제시한다.
- 모범 용어("확장 가능하게", "깔끔하게")·관습("보통 앱들처럼")·"~해야 할 것 같아요"가 목표 자리에 오면 **"누구에게도 설명할 필요가 없다면, 실제로 뭘 원하세요?"**로 탐침한다.

**의도는 있는데 방향이 여러 갈래일 때 — 넓혔다 좁히기**

1. "어떻게 하면 <누가> <무엇을> 할 수 있을까?" 한 문장(HMW)으로 문제를 고정한다.
2. 변형안 5~8개 — `references/interview-techniques.md`의 렌즈 중 맞는 것만 골라 쓰고, 각 안에 존재 이유 한 줄과 근거 코드 경로를 붙인다(관련 코드가 없으면 "근거 코드 없음"으로 밝힌다). 20개짜리 얕은 목록 금지.
3. 사용자 반응을 받아 서로 의미 있게 다른 방향 2~3개로 묶고, 사용자 가치·실현성·차별성으로 점검한다.
4. 묶은 방향마다(첫 턴의 변형안 단계가 아니라 3번에서 방향을 묶을 때) **숨은 가정**(검증 안 됐는데 걸고 있는 것, 이 안을 죽일 수 있는 것, 일부러 무시하는 것)을 드러낸다 — 생략 금지.
5. 약한 안에는 근거를 들어 솔직하게 반대한다. 사용자가 방향 하나를 고를 때까지 기다린다.

### 3. 멈춤 조건

**다음 질문 3개에 대한 사용자 반응을 예측할 수 있고, 방향이 하나로 정해졌으면** 4단계로 간다.
몇 차례 물었는데도 확신도가 오르지 않으면 질문이 틀린 것이다 — 그 사실을 말하고 프레임을 바꾼다.

### 4. 정련 요약 — 사용자의 말로

논의에서 모인 답·결정을 아래 형식으로 정련해 보여준다. 대화에서 나오지 않은 값은 지어내지 않는다(비면 "미정"). 원래 요청 원문을 첫 줄에 남긴다 — 이 요약이 frd-author의 `FRD.draft.md`로 보존되므로 인터뷰 전 원문도 함께 남는다.

```markdown
## 기능 정련 요약 — <기능 이름>
- 원래 요청:     <처음 받은 요청·아이디어 원문 그대로>
- Outcome:      <무엇이 달라지는가>
- User:         <누가 혜택을 받는가>
- Why now:      <왜 지금인가>
- Success:      <됐다고 판단하는 기준, 가능하면 측정값>
- Constraint:   <넘을 수 없는 제약>
- Out of scope: <이번에 하지 않을 것과 이유 — 최소 1개>
- 방향:          <고른 방향과 이유, 근거 코드 경로> (방향 탐색을 안 했으면 생략)
- 논의 중 결정:  <인터뷰 중 사용자가 정한 정책·규칙·우선순위>
- 가정:          <검증 안 된 채 참으로 두는 것 — 확인 방법>
- 남은 질문:     <답이 보류된 것, 없으면 "없음">

이대로 FRD 정련으로 넘어갈까요? 고칠 부분이 있으면 말씀해 주세요.
```

**Out of scope는 생략 불가** — 어긋남의 절반은 "만들지 않을 것"에 대한 말 없는 불일치다.

### 5. 명시 승인 → frd-author로 바로 이어서

- 통과는 요약을 그대로 받아들인다는 명시 표현("네"·"맞아요"·"좋아요, 진행해 주세요" 등)뿐이다. "알아서 해주세요"는 결정 위임이므로 구체 선택지 2개로 다시 묻는다. 수정이 오면 반영해 4단계를 다시 보여준다.
- 승인되면 **같은 흐름에서** 다음 단계로 넘어간다(다시 묻지 않는다).
  - **단독 호출이면** Skill 도구로 `devoks-sdlc:feature-frd-author`를 실행한다 — `frd`는 생략한다(기본값 "대화 초안" = 방금 승인된 정련 요약). `out`을 받았으면 함께 넘긴다.
  - **frd-author 또는 `feature-workflow-runner`의 Phase 0 게이트에서 진입했으면** 스킬을 새로 호출하지 않고 그 호출자의 절차로 돌아간다(승인된 요약이 그 초안이 된다).
- 사용자가 "정리만 하고 FRD는 나중에"라고 하면 그때만 워크스페이스를 확정해 `<out>/FRD.draft.md`로 요약을 저장하고(`output-location.md` 보존 형식, 기존 파일이 있으면 맨 아래에 추가) 멈춘다 — 대화가 끊기면 요약이 사라지기 때문이다. 나중에 `/devoks-sdlc:feature-frd-author frd=<out>/FRD.draft.md`로 이어간다.

## 완료 기준

- 첫 턴에 가설 + 확신도가 있었고, 70% 미만 확신도에는 이유가 붙었다.
- 의도 질문은 한 번에 하나씩 예상 답과 함께 나갔다. 방향 탐색을 했다면 변형안·방향 점검·숨은 가정이 있었다.
- 정련 요약(Out of scope 포함)을 사용자가 명시적으로 승인했다.
- 승인 직후 frd-author(또는 진입한 호출자 절차)로 이어졌다 — 보류 요청이면 `FRD.draft.md`에 저장됐다.
