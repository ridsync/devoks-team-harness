## 1. 문서 경계 (PRD / TRD / FRD)

| 내용 | PRD | TRD | FRD |
|---|---|---|---|
| 무엇을·왜, NFR 요구 | ● | 참조 | 참조 |
| 기술스택·시스템 구성·공유 도메인 모델 | 제약만 | ● | 따름 |
| NFR·불변식 보장 위치와 검증 레벨 | | ● | 기능 단위로 구체화 |
| 기능 하나 안의 컴포넌트·패턴 (FRD §4) | | ✕ | ● |
| 엔드포인트·파라미터·상태 전이 (FRD §5) | | ✕ (규약만) | ● |
| EARS AC·Edge | | ✕ | ● |

판단 질문: **"이 결정이 바뀌면 여러 기능이 같이 바뀌는가?"** → 그렇다면 TRD. 하나만 바뀌면 FRD.
넣지 않는 것: 일정·공수, 비용 산정(비용 상한은 제약으로만), 클래스 수준 설계.

## 2. 사실과 판단 — 입력 확인 규칙

| 구분 | 예 | 없을 때 |
|---|---|---|
| 사실 | 기존 코드·운영 시스템, 조직 표준 기술, 호스팅·데이터 위치, 연동 대상, 보안·규제 요건, 팀 역량 | 묻는다(HITL, 한 번에) — 답이 없으면 `미확정`, 그 위에 내린 결정은 §9·§12에 가정으로 남긴다 |
| 판단 | 스택, 구성요소 분할, 저장소, 인증 방식, API 스타일, 불변식 보장 위치 | 대안 비교와 함께 `제안: X — Y·Z 대비 <NFR-n·제약> 때문`으로 제시하고 사실 질문과 **같은 메시지**에서 확인 |

- 확인은 한 번에: 사실 질문 + 판단 제안을 한 메시지에 묶는다. 하나씩 묻지 않는다 — 무엇을 만들지는 이미 PRD가 정했으므로 의도를 좁힐 대화가 필요 없다.
- PRD §7 제약·NFR, 저장소 README·설정 파일에서 확인할 수 있는 사실은 묻지 않는다(근거 경로 인용).
- 비-HITL: 묻지 않는다. 사실은 `미확정`, 판단은 제안값 그대로 쓰고 결과 보고에 확인 목록을 남긴다.

## 3. 스택 선택 규칙

1. **NFR·제약에서 출발한다.** 각 선택의 이유 열에 NFR-n·제약·팀 역량 중 최소 하나를 연결한다. 연결이 없는 선택은 취향이다 — 대안 비교로 다시 본다.
2. **대안을 최소 1개 비교한다.** "아무것도 추가하지 않음"(기존 것 재사용)도 대안이다.
3. **팀 역량과 조직 표준이 기술적 우위보다 먼저다.** 에이전트가 구현해도 운영·리뷰는 사람이 한다.
4. **버전·지원 여부·가격 같은 시점 의존 정보는 확인하고 출처를 적는다.** Context7 MCP가 있으면 우선, 없으면 공식 문서 웹 검색. 확인하지 못했으면 버전을 적지 않고 "§11 확인 필요"로 둔다 — 기억으로 쓴 버전은 틀리기 쉽다.
5. **stack preset을 매핑한다.** devoks-core preset: `react-web` · `react-native` · `android` · `ios` · `python-fastapi`. 맞는 것이 있으면 §2에 적고 `/devoks-core:setup-project-convention` 실행을 안내한다(자동 실행 금지). 없으면 "해당 없음".

## 4. brownfield 모드

판별: `<out>`이 속한 저장소에 애플리케이션 코드(패키지 매니페스트·소스 디렉터리)가 있거나, 입력 사실 1번이 기존 코드베이스를 가리키면 brownfield.

- **기존 스택은 사실이다.** 매니페스트·설정 파일에서 읽어 §2에 "현행"으로 적고 근거 경로를 출처 열에 둔다. 재선정하지 않는다.
- **결정은 변경분만.** PRD 요구를 맞추려면 바꾸거나 더해야 하는 것(새 저장소, 인증 교체, 모듈 분리 등)만 대안 비교·ADR로 남긴다.
- §3·§4는 현재 구조를 기록하고, PRD 요구에 비춰 빈 곳(없는 엔티티·경계)을 표시한다.
- 구조 파악은 가볍게(디렉터리·매니페스트·진입점). 깊은 모듈 분석이 필요하면 `devoks-sdlc:code-analyze-module`을 안내한다.

## 5. NFR·불변식 보장 설계

- **불변식은 우회할 수 없는 가장 낮은 레이어에서 보장한다.** 예: "이중 예약 0건" → DB 유니크/배타 제약 또는 서버 트랜잭션. 클라이언트 검증만으로는 동시 요청을 막지 못한다.
- 각 NFR 행에 **검증 레벨**을 적는다(단위/통합/E2E/부하). FRD의 Testing Strategy와 PLAN의 DoD가 이 열을 따른다.
- 수치 NFR(응답 시간 등)이 PRD에서 `제안`이면 TRD에서도 제안 상태 그대로 참조한다 — TRD가 확정하지 않는다.

## 6. 기반 작업 (B-n)

- 기준: 사용자 기능이 아니지만 **둘 이상의 F-n이 의존**하는 것 — 프로젝트 골격, 인증 기반, 공유 데이터 모델·마이그레이션, CI·환경, 계측 파이프라인.
- greenfield는 보통 "골격 + 최소 CI"(walking skeleton)가 B-1이다. brownfield는 PRD 요구를 위해 새로 필요한 기반만.
- **FRD 시드는 `FEATURES.md`의 "기반" 구역이 SSOT** — FRD 입력 양식(`../feature-frd-author/assets/FRD.intake.md`)을 **`## 기능 정련 요약 — <B-n 이름>` 헤더까지 그대로** 쓴다(코드 블록 안에). 기존 FEATURES.md의 F-n 시드가 구형식이어도 B-n은 이 형식을 따른다 — frd-author는 이 헤더로 입력 양식을 알아보고 의도 게이트를 건너뛴다. Outcome은 "이후 기능이 무엇을 할 수 있게 되는가", User는 "개발자(에이전트) / 이후 기능 F-n"으로 쓴다.
- TRD §10에는 ID·이름·선행 대상만 둔다. 이 구역은 이 스킬이 소유하고, `product-prd-author`는 갱신 모드에서 건드리지 않는다.

## 7. 자체 점검 체크리스트

- [ ] §2 모든 선택에 대안 ≥1과 이유(NFR-n·제약·팀 역량 연결)가 있다. 시점 의존 정보에 출처가 있거나 §11로 갔다.
- [ ] brownfield면 기존 스택이 근거 경로와 함께 "현행"으로 적혔고 재선정되지 않았다.
- [ ] PRD의 모든 NFR(불변식 포함)이 §6에 보장 위치·검증 레벨과 함께 있다.
- [ ] PRD §4의 모든 계측 FR이 §7에 이벤트로 있다.
- [ ] §4에는 둘 이상의 F-n이 쓰는 엔티티만 있다.
- [ ] 엔드포인트 목록·EARS AC·기능 내부 컴포넌트가 없다.
- [ ] 모든 B-n이 FEATURES.md 기반 구역에 FRD 시드로 있고, 의존 순서가 릴리스 순서와 모순되지 않는다.
- [ ] 모든 `미확정`·`제안`이 §11에 대응하고, 주요 판단이 §12 ADR로 남았다.

## 8. 갱신 모드

- 계기: PRD 버전이 TRD의 `prd_version`보다 높거나, 기술 결정을 바꾸자는 요청.
- 먼저 변경 목록(섹션·ID·연쇄 영향: 엔티티→기능, 불변식→FRD AC)을 만들고 **확인 후** 쓴다. 비-HITL이면 보고만 한다.
- bump: major = 핵심 스택·배포 구조 교체 / minor = 구성요소·엔티티·NFR 보장·B-n 추가·변경 / patch = 의미 불변 정정·미확정 해소.
- ADR은 지우지 않는다. 바뀐 결정은 새 ADR을 추가하고 기존 것을 `superseded by ADR-n`으로 표시한다.
- 영향받는 FRD(FEATURES.md 상태 `frd` 이후)는 경로와 함께 "재검토 필요"로 보고한다(직접 고치지 않는다).
