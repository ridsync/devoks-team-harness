# 소형 필라테스 센터 예약 앱 — Product Requirements Document

> **개요:** 강사 2~5명 규모 소형 필라테스 센터의 원장과 회원을 위한 예약 앱이다. 지금 원장은 카카오톡으로 하루 30건 넘는 예약·변경 문의를 받아 엑셀에 옮겨 적는데, 반영 누락 때문에 더블부킹이 월 4~5건 생긴다. 회원이 직접 예약·변경하고 회원권 차감이 자동으로 이루어지는 단일 예약 원장을 만들어 원장의 응대 부담과 예약 오류를 없애고, 수업 전 알림으로 노쇼를 줄이는 것이 목표다. 개발자 1명·디자이너 0.5명으로 3개월 안에 iOS/Android 첫 버전 출시를 목표로 한다.
>
> 이 문서는 제품 단위의 What·Why만 다룬다. 기능별 AC·Contract·Edge는 각 FRD, 기술 설계는 TRD가 소유한다.
> 표기: 답이 없는 칸은 `미확정`, 판단 값의 출발점은 `미확정 (제안: <값> — <근거>)` — 둘 다 §11에서 확인한다.

## 1. 문제 정의
- **문제 진술:** 소형 필라테스 센터 원장이 / 회원 예약·변경을 카카오톡으로 받아 엑셀에 수기 반영하는 상황에서 / 예약 현황을 정확히 유지하려다 / 메신저 응대와 수기 이중 입력 때문에 / 하루 30건 넘는 문의 응대에 시간을 쓰고 월 4~5건의 더블부킹이 생긴다.
- **JTBD:** 회원이 수업을 잡거나 바꾸려 할 때, 원장인 나는 일일이 답하고 옮겨 적지 않아도 예약이 정확히 반영되기를 원한다, 그래서 응대 대신 수업과 센터 운영에 집중할 수 있도록.
- **Why now:** 미확정 (입력에 없음 — §11 Q-12)
- **근거:** 대표 미팅 메모(`sources/pilates-requirements.md`) — "하루 평균 30건 넘는 예약/변경 문의를 카톡으로 응대", "엑셀 반영 누락으로 더블부킹이 월 4~5건". 노쇼가 많다는 진술은 수치 없음(가정 A-1과 연결).

## 3. 가치 제안 & 대안
- **핵심 가치 (한 문장):** 소형 센터가 감당할 수 있는 범위의 기능만으로, 회원이 직접 예약·변경하고 회원권이 자동 정산되어 원장이 메신저 응대와 수기 기록에서 벗어난다.

| 대안 | 사용자가 겪는 한계 | 우리의 차이 |
|---|---|---|
| 아무것도 안 함 (카톡+엑셀 유지) | 하루 30건+ 응대, 수기 반영 누락으로 더블부킹 월 4~5건, 회원권 잔여 수기 계산 | 회원 셀프 예약 + 단일 예약 원장 + 자동 차감 |
| 대형 예약 SaaS (제품명 미확정) | 원장 의견: 월 구독료가 비싸고 기능이 너무 많음 | 소형 센터 핵심 과업(예약·회원권·알림)에 한정한 범위. 가격 차이는 수익화 모델 미확정(Q-1) |

- **수익화 지점:** 미확정 — 특정 센터 전용 앱인지 여러 센터 대상 서비스인지부터 미확정(Q-1). 회원 결제는 현장 결제 유지(MVP 범위 아님).

## 5. 핵심 시나리오
- **S-1 회원 셀프 예약:** 회원이 다음 주 수업을 잡고 싶을 때 원장에게 메시지를 보내지 않고 앱에서 수업 일정과 남은 자리를 확인한 뒤 바로 예약한다. 예약은 즉시 확정되어 원장의 예약 현황에 반영되고, 회원은 자신의 회원권 잔여 횟수를 함께 확인한다.
- **S-2 회원 셀프 변경·취소:** 일정이 생긴 회원이 센터가 정한 취소 정책 범위 안에서 직접 예약을 취소하거나 다른 수업으로 바꾼다. 비게 된 자리는 다른 회원이 바로 예약할 수 있다.
- **S-3 원장의 하루 운영:** 원장은 오늘과 이번 주의 수업별 예약자·빈 자리를 한 번에 보고, 앱을 쓰지 않는 회원의 전화·현장 요청은 대신 처리한다. 수업이 끝나면 출석·노쇼를 기록하고, 회원권 잔여 횟수는 정책에 따라 자동으로 맞춰진다.
- **S-4 수업 전 알림:** 예약한 회원은 수업 전에 알림을 받아 일정을 다시 확인하고, 못 오게 되면 취소 기한 안에 취소한다.

## 7. 제약 & 제품 공통 비기능 요구
**제약** (넘을 수 없는 것)
- 일정·인력·예산: 개발자 1명 + 디자이너 0.5명, 3개월 안에 첫 버전 출시 목표 (메모). 기준 시작일·예산 미확정 (Q-12).
- 플랫폼·기기: iOS와 Android 모두 지원 (메모).
- 기존 시스템·외부 API 연동: 결제는 현장 결제 유지 — 결제 연동 없음 (메모). 기존 엑셀 데이터 이관 여부 미확정 (Q-11). 메모의 "Firebase로 푸시"는 기술 선택이라 제약이 아닌 TRD 입력으로 넘긴다 (Q-6).
- 법규·정책: 회원 연락처와 건강 특이사항을 다룬다 (메모). 건강 정보의 법적 분류(민감정보 해당 여부)와 그에 따른 동의·보관 요건은 미확정 (Q-9).

**공통 NFR** (여러 기능에 걸치는 것 + §4에서 올라온 제품 불변식·계측 요구 — FRD는 이 ID를 참조)
| ID | 분류 | 요구 (측정 가능한 기준) |
|---|---|---|
| NFR-1 | 정합성 (제품 불변식) | 한 수업의 확정 예약 수는 정원을 넘지 않고, 같은 회원이 같은 수업에 중복 예약되지 않는다 — 동시 예약 요청을 포함해 위반 0건. 더블부킹의 정확한 정의(정원 초과 외 강사·기구 중복 포함 여부)는 미확정 (Q-8) |
| NFR-2 | 정합성 (제품 불변식) | 회원권 잔여 횟수 = 부여 − 차감 + 복원이 항상 성립하고 음수가 되지 않으며, 모든 변동은 사유·시각·처리 주체와 함께 남는다 |
| NFR-3 | 성능·사용성 | 메모의 "빠르고 간편하게" → 미확정 (제안: 앱 진입부터 예약 확정까지 조작 3단계 이내, 예약 요청 응답 1초 이내 — 메신저로 묻는 것보다 빨라야 셀프 처리로 옮겨옴) |
| NFR-4 | 보안·프라이버시 | 건강 특이사항은 원장(및 권한을 받은 강사)만 열람할 수 있고 다른 회원에게 노출되지 않는다. 수집 동의·보관 기간은 미확정 (제안: 건강 특이사항은 별도 동의 후 수집, 탈퇴 시 파기 — 건강 정보 보호 관행) |
| NFR-5 | 가용성·알림 | 미확정 (제안: 리마인드 알림 발송 성공·실패가 회원·수업 단위로 기록되고, 실패 시 재시도 — 노쇼 감소 가정 A-1 검증에 발송 여부 데이터가 필요) |
| NFR-6 | 플랫폼 | 회원 기능은 iOS·Android에서 동일한 능력을 제공한다 (원장 기능의 제공 기기는 미확정 — Q-7) |

## 8. 범위
- **MVP:** 가설 — "회원이 직접 예약·변경하고 회원권이 자동 차감되면 원장의 메신저 응대가 줄고 더블부킹이 사라지며, 수업 전 알림이 노쇼를 줄인다." 포함 FR: FR-1 ~ FR-15.
- **우선순위 원칙:** 미확정 (제안: 예약 정합성(NFR-1·2) > 회원 셀프 예약·변경(핵심 KPI) > 노쇼 알림(가정 A-1 검증) > 원장 편의 — 3개월·1인 개발 제약에서 정합성이 깨지면 엑셀보다 못하기 때문)

| Out of Scope | 이유 | 행선지 |
|---|---|---|
| 온라인 결제 (FR-16) | 메모: "결제는 일단 현장 결제 유지, 온라인 결제는 나중에" | 다음 버전 이후 (Later) |
| 매출·정산 통계, 쿠폰·마케팅 등 운영 부가 기능 | 미확정 (제안: 제외 — 대형 SaaS의 "기능 과다"가 대안의 한계로 지목됐고 3개월·1인 개발 제약) | 미확정 (제안: 검증 후 재검토) |

## 12. 용어집 (선택)
| 용어 | 정의 |
|---|---|
| 회원권 | 회원이 센터에서 구매한 수강권. MVP 확인 범위는 횟수제(예: 10회권) |
| 더블부킹 | 같은 수업(또는 자원)에 수용 가능 수를 넘는 예약이 확정되는 상태 — 정확한 범위는 Q-8 |

| 셀프 처리 | 원장을 거치지 않고 회원이 앱에서 직접 수행한 예약·변경·취소 |
