# ADR (Architecture Decision Record) 작성 규칙 (SSOT)

> **되돌리기 어려운 아키텍처 결정**과 그 **이유**를 저장소에 한 결정당 파일 하나로 남긴다.
> ADR의 존재 이유는 하나다 — 코드·커밋·PR에는 "무엇을 했는지"만 남고 "왜 다른 안이 아니라 이것인지"는 남지 않는다. 그 빠진 이유를 남긴다.
> 이 문서가 대상 판정·분량·형식·위치·상태 전이의 단일 기준이다. 결정이 나오는 스킬(TRD·FRD·리팩토링·PLAN 실행)은 규칙을 다시 쓰지 않고 이 문서를 가리킨다.

## 1. 대상 판정 — 세 관문을 모두 통과해야 ADR이다

ADR은 드물어야 한다. 아래 **세 관문을 모두** 통과한 결정만 쓴다. 하나라도 걸리면 ADR이 아니다(§1-3의 다른 기록 위치로 보낸다).

| 관문 | 질문 | 통과 예 | 탈락 예 |
|---|---|---|---|
| **A. 범위** | 아키텍처 결정인가? — 시스템 구성·배포 구조, 앱 내부 계층·모듈 경계, 핵심 플랫폼·라이브러리 채택(데이터 접근·인증·상태·통신처럼 코드 전반이 기대는 것), 데이터 저장·도메인 모델 구조, 공개 계약(API·이벤트·인증 경계), 품질 속성(NFR·불변식) 보장 방식 | 진입점→서비스→DAL 계층, ORM+codegen 채택, 웹·모바일 공용 REST, soft-delete·이력 테이블 | 브랜드·모티프·비주얼 톤·모션 연출, 화면 구성, 디자인·작업 프로세스(와이어프레임 단계 도입 등), 개발 도구 사용 여부(Storybook 등), 제품 범위(알림 채널·MVP 제외) |
| **B. 되돌리기 비용** | 나중에 바꾸면 데이터 이주·공개 계약 변경·여러 모듈 재작성이 필요한가? | DB·데이터 위치, 계층 구조, 인증 방식 | 개발 도구 하나 추가·제거, 설정값, 기능 하나 안의 설계 |
| **C. 이유가 코드에 없다** | 실재한 대안과 트레이드오프가 있었고, 그 선택 이유가 코드·커밋·PR만으로는 드러나지 않는가? | 관례(공식 권장·preset)와 다르게 갔다, 대안이 실제로 유력했다 | 주류 기본값·preset 그대로 택했다, 대안 비교가 형식뿐이다, 이유가 "사용자 결정"·"유지비 절감" 한마디뿐이다 |

**관문 적용 세칙:**
- **B는 결정이 실행된 뒤의 비용으로 본다.** 아직 착수 전이고 미뤄도 손해가 없는 계획 결정(예: 이후 이전할 인프라 대상)은 TRD §9·§11에 두고, 착수가 확정될 때 ADR로 판정한다.
- **B는 결정한 구조 자체를 평가한다.** 어댑터·경계를 두기로 한 결정이면 그 경계 구조가 대상이고, 경계 안에서 쉽게 바꾸는 공급자·모델·설정값은 TRD 행이다.
- **C의 이유는 구체적 제약을 가리켜야 한다** — NFR-n·불변식·기존 구조·외부 사실·공식 권장과의 차이 중 하나 이상. "비용 절감"·"단순함"·"사용자 결정" 같은 가치어만 있으면 탈락이다.

**판정 질문 하나로 줄이면:** "1년 뒤 새 팀원이 이 결정을 뒤집으려 할 때, 이 문서가 없으면 비싼 실수를 하는가?" — 아니면 ADR이 아니다.

> 오류 비용: 과다 기록은 노이즈만이 아니다 — 빈약한 ADR이 쌓이면 정말 중요한 결정이 묻히고, 아무도 ADR을 읽지 않게 된다. 그래서 애매하면 **쓰지 않는 쪽**이 기본이다. 제안할 때도 관문 판정 근거를 함께 보이고 사용자 확인 후에만 기록한다(§4).

### 1-1. 묶음 단위 — 한 ADR = 함께 되돌려야 하는 결정 하나

- **잘게 쪼개지 않는다.** 언어·프레임워크·라이브러리·도구를 항목마다 ADR로 만들지 않는다. 언어·런타임 선택이 관문을 통과해도 단독 ADR로 두지 않고, 그 선택을 요구한 상위 결정(예: 웹·모바일 공용 스키마 계약)의 ADR에 대안·이유로 넣는다. 함께 바뀌어야만 의미가 있는 선택(예: 프레임워크 + 렌더링 전략, ORM + 스키마 codegen + 마이그레이션 방식)은 하나의 ADR로 묶는다.
- **초기 스택 기준선은 ADR 목록이 아니다.** 레이어별 선택·대안·이유는 TRD §2 표가 기록한다. 그중 세 관문을 통과한 결정만 ADR로 올린다 — 신규 제품 TRD에서도 보통 몇 개(시스템 구성·데이터 저장·인증 경계·앱 내부 계층 수준)에 그친다. 스택 행 수만큼 ADR이 생겼다면 판정을 잘못한 것이다.
- **묶을지 나눌지는 "독립적으로 되돌릴 수 있는가"로 정한다.** 상위 결정을 그대로 둔 채 하위 선택만 바꿀 수 있으면 하위 선택을 따로 판정하고(관문 미통과면 TRD 행), 상위를 바꾸면 반드시 같이 바뀌면 한 ADR로 묶는다. 예: AI 생성 파이프라인 경계(ADR) ⊃ 경로별 모델·마감값(TRD 행), 계층 구조(ADR) ⊃ 리소스 인가를 DAL에 둔다(같이 바뀌므로 같은 ADR).
- **같은 결정의 세부는 새 ADR이 아니다.** 이미 있는 ADR의 범위 안에서 정하는 세부(설정값·버전·파일 위치)는 그 ADR이 가리키는 문서(TRD·convention)를 고친다.

### 1-2. 회색 지대 — 올리는 경우

- **도메인 규칙이 기술 구조를 고정할 때**: 규칙은 PRD에, 그 규칙을 구현하는 구조 선택은 ADR에 두고 서로 링크한다. 예: "주문은 삭제하지 않는다"(PRD) → soft-delete·이력 테이블(ADR), "금액은 원 단위 정수"(PRD) → 금액 타입·정밀도 규약(ADR).
- **버그 수정이 구조적 원인을 드러내 방식을 바꿀 때**: 수정은 PR에, "앞으로 이 방식으로 한다"는 규약만 ADR에. 예: 중복 결제 → idempotency key 전면 도입.
- **디자인 결정이 기술 구조를 고정할 때**: 디자인 자체(모티프·톤·모션 연출)는 VISUAL.md에, 그것이 강제하는 **구조**(예: 웹·모바일 공용 토큰 패키지 분리, 단일 토큰 원본에서 플랫폼별 산출물을 생성하는 파이프라인)가 관문 B·C를 통과하면 그 구조만 ADR로 쓴다.

### 1-3. ADR이 아닌 것 → 기록 위치

| 결정 | 기록 위치 |
|---|---|
| 제품·도메인 정책, 기능 범위 (What) | PRD §13 / FRD |
| 스택 레이어별 선택·대안·이유 중 관문 미통과 | TRD §2·§2.1 표 행 |
| 앱 내부 구조의 실행 규칙(폴더 표·import 제한·명명) | TRD §3.1 · `.claude/rules/project-convention.md` |
| 브랜드·비주얼·모티프·모션 원칙, 에셋 정책 | VISUAL.md (구현 수단만 TRD §2.1 행) |
| 개발 도구·작업 프로세스(문서 단계, 컴포넌트 카탈로그 도구 등) | TRD §8 개발 기반 / 해당 스킬 문서 |
| 테스트 도구·방식 | TRD §8 + `project-convention` Testing |
| 데이터 보존·개인정보 정책 | PRD(정책) + TRD §6(보장 방식) |
| 계측 이벤트·구성 | TRD §7 |
| 설정값(모델 배정·타임아웃·버전·환경변수) | TRD 해당 절 행 / 설정 파일 |
| 기능 하나 안에서 끝나는 설계 | FRD §4 `DSN` |
| 기존 패턴을 따른 구현, 버그 수정 자체, 이주 절차 | PR·커밋 / PLAN |
| 에이전트 작업 선호 | 메모리 |
| 현재 구조 설명 | `ARCHITECTURE.md`·README |

## 2. 위치·이름

```
docs/decisions/
├─ ADR-001-server-state-tanstack-query.md
├─ ADR-002-monorepo-pnpm-workspaces.md
└─ ...
```

- 파일 하나 = 결정 하나. 이름은 `ADR-NNN-<kebab-slug>.md`(3자리 일련번호). 번호는 실행 시 `ls docs/decisions/` 로 기존 최대값을 확인해 +1 한다(추측 금지). 번호는 재사용하지 않는다.
- 별도 색인 파일을 두지 않는다 — 디렉토리 목록(번호·slug)과 각 파일 frontmatter `status`가 색인이다. 제품 TRD가 있으면 TRD §12가 **TRD가 의존하는 ADR의 색인**(ID·제목·상태·링크)을 겸한다. 본문은 ADR 파일에만 둔다(두 곳에 본문을 쓰면 drift).
- `docs/` 레이아웃 SSOT: `output-location.md`.

## 3. 형식·분량 — 짧고, 이유가 중심

`../assets/ADR.template.md`를 따른다 — frontmatter(`id`·`title`·`status`·`date`·`supersedes`·`superseded_by`·`source`) + `Context` / `Decision` / `Rationale` / `Considered Alternatives` / `Consequences` / `Revisit Conditions` / `Related`. 섹션 제목은 영어로 고정하고(헤더 구조를 바꾸지 않는다), 본문은 한국어로 쓴다.

**분량:** 한 화면에 읽혀야 한다 — 본문(frontmatter 제외) 40줄 안팎을 목표로 한다. 이를 크게 넘으면 아래 "쓰지 않는 것"이 섞였는지 먼저 점검한다(줄 수는 점검 신호이지 판정 기준이 아니다).

| 섹션 | 쓰는 것 | 분량 |
|---|---|---|
| Context | 이 결정을 강제한 요구·제약(NFR-n·불변식·기존 구조·외부 사실)과 현재 문제 | 2~5줄 |
| Decision | 무엇을 택했는가 — "~로 한다" 능동형. 검토 중이면 ADR이 아니라 오픈 이슈(TRD §11·FRD §10) | 1~3문장 |
| Rationale | 왜 이 트레이드오프를 받아들였는가 — Context의 어떤 요구·제약을 이 안이 충족하는지 연결. 근거 사실·공식 문서는 출처를 붙인다 | 불릿 2~4개 |
| Considered Alternatives | **기각한** 대안만, 각각 장점과 기각 이유. 채택안 행은 두지 않는다 | 1~3행 |
| Consequences | 감수하는 비용·제약, 이후 코드가 지킬 규약(상세 규칙은 링크) | 불릿 2~4개 |
| Revisit Conditions | 어떤 사실이 바뀌면 다시 여는가 — 관찰 가능한 조건 | 1~3개 |
| Related | 관련 PRD/TRD 절·ADR·공식 문서 링크 | 필요한 것만 |

**쓰지 않는 것** (커밋·PR·다른 문서가 이미 담는다):
- 구현 경위·작업 목록·변경 파일 목록·이주 절차·rename 범위 → PR·PLAN
- 폴더 표·import 제한 목록·설정값·명령·명명 규칙 같은 실행 규칙 전문 → TRD §3.1·project-convention에 두고 ADR은 결정의 골자와 링크만. 구분: **골자**는 이 결정을 기각한 대안과 구별하는 데 필요한 것(계층과 의존 방향, 진입점별 데이터 경로 원칙, 인가를 두는 위치), **실행 규칙**은 그 결정을 지키기 위한 열거(경로 목록, import 금지 목록, 설정값)다
- Rationale을 반복하는 "좋아지는 것"
- 빈 칸 메우기 문구 — "Rationale 참고", "기록 없음", "이전 기록에 별도 항목 없음", "Decision을 따른다". 칸을 채울 내용이 없으면 관문을 다시 의심한다: 이유·대안·감수 비용을 하나도 쓸 수 없는 결정은 ADR이 아니다.

**품질 규칙:**
- Rationale에 "사용자 결정"만 적지 않는다 — 사용자가 정했어도 그 이유(제약·우선순위)를 묻거나 대화에서 찾아 적는다. 이유를 끝내 알 수 없으면 ADR로 쓰지 않는다.
- 대안은 실제로 비교한 것만 쓴다. 비교한 대안이 없으면 관문 C 미통과다 — 대안을 꾸며 넣지 않는다.
- 버전·지원 여부·가격 같은 시점 의존 사실은 출처(공식 문서 링크)를 붙이고, 확인 못 했으면 `미확정`.
- 날짜는 실행 시 `date +%Y-%m-%d`로 구한다.

## 4. 작성 절차 — 판정 → 제안 → 확인 → 기록

1. **판정** — 작업 중 결정이 나오면 §1 세 관문을 돌린다. 통과한 것만 "ADR 후보"로 표시하고, 탈락한 것은 §1-3 위치에 기록한다(TRD면 해당 절 표 행).
2. **제안** — 후보마다 결정·기각한 대안·이유와 **관문 판정 근거 한 줄**(예: "B: 바꾸면 전 테이블 이주 / C: 공식 권장과 다름")을 담아 "ADR-NNN으로 남길까요?"를 묻는다. 다른 확인 질문과 같은 메시지로 묶는다(확인을 늘리지 않는다). 여러 결정을 한 번에 다루는 작업(TRD 등)이면 "ADR로 올릴 것 N개 / 표에만 남길 것"을 나눠 보인다.
3. **기록** — 확인되면 `status: accepted`로 파일을 쓴다. 사용자가 거절하면 쓰지 않는다.
4. **비-HITL**(오케스트레이터·서브에이전트 경로) — 묻지 않는다. 관문을 통과했고 결정이 확정 산출물(예: TRD 제안값)의 일부면 `status: proposed`로 쓰고 보고의 확인 목록에 올린다. 그 밖에는 쓰지 않고 "ADR 후보"로 보고만 한다. `accepted`는 사용자 확인 후에만 붙인다.
5. 서브에이전트(`code-implementer` 등)는 ADR을 쓰지 않는다 — 결정이 필요하면 리포트로 올리고 메인 루프가 이 절차를 밟는다.
6. 사용자가 관문 미통과 결정을 ADR로 남기라고 명시하면 따르되, 탈락 관문과 대신 둘 위치를 한 줄로 알린다.

## 5. 불변성·상태 전이

- `proposed` → `accepted`(확인됨) → `superseded`(새 ADR로 대체) 또는 `deprecated`(대체 없이 폐기).
- `accepted` 이후 본문은 고치지 않는다(오탈자·링크 정정만). 결정이 바뀌면 **새 ADR**을 쓰고 `supersedes: ADR-old`, 기존 파일은 `status: superseded`·`superseded_by: ADR-new`만 바꾼다. 지우지 않는다.
- 현재 구조 설명(`ARCHITECTURE.md` 등)은 계속 고쳐 쓰는 스냅샷이고 ADR은 이유의 이력이다 — 서로 링크만 건다.
- **이미 쌓인 관문 미통과 ADR**은 자동으로 정리하지 않는다. 사용자가 정리를 요청하면 파일마다 판정(유지 / 상위 ADR로 통합 / 다른 문서로 이관 / 분할)을 표로 제안하고, 확인 후:
  - 통합·이관: 원 파일은 `status: deprecated`와 본문 첫 줄에 옮긴 위치를 적는다(삭제하지 않는다 — 다른 문서의 `ADR-NNN` 참조가 끊기지 않게).
  - 분할(한 파일에 통과·미통과 결정이 섞임): 통과 부분만 새 ADR(`supersedes: ADR-old`)로 쓰고 나머지는 이관한다. 원 파일은 `superseded`.
  - 형식만 미달(관문 통과, 빈 칸 메우기·과다 분량): accepted 본문은 고치지 않으므로, 사용자가 원하면 같은 결정을 새 형식으로 다시 쓴 ADR로 대체한다(`supersedes`). 원하지 않으면 그대로 둔다.
  - 이미 `superseded`·`deprecated`인 파일은 정리 대상이 아니다.

## 6. 작성 지점 (스킬별)

| 지점 | 언제 | 처리 |
|---|---|---|
| `product-trd-author` | §2~§6 판단 확정 시 | 모든 판단은 TRD 해당 절 표에 선택·대안·이유로 남긴다. **§1 관문을 통과한 판단만** ADR 파일로 쓰고 §12에 색인 행 — 판단마다 쓰지 않는다 |
| `feature-frd-author`·`feature-workflow-runner` (FRD §4) | `DSN`이 §1 관문을 통과할 때(기능 밖으로 파급·되돌리기 어려움·이유가 코드에 없음) | ADR로 **승격** — DSN 근거 칸에 `ADR-NNN` 기재, 본문은 ADR에 |
| `code-refactoring` | 계획에 구조 방향 전환(계층 재편·의존 방향·패턴 교체)이 있을 때 | 계획 승인 메시지에서 함께 제안 |
| `feature-plan-executor` | 구현 중 PLAN에 없던 결정(새 핵심 의존성·구조 변경)이 생겼을 때 | 마무리 보고에 "ADR 후보"로 올리고 확인 후 기록 |
| `product-design-author` | — | ADR을 만들지 않는다. 기술 구조에 영향이 있으면 "TRD 갱신 필요"로 보고하고 TRD 갱신 모드가 §1로 판정한다 |
| 그 밖의 작업 | 스킬 밖 대화에서 위 결정이 내려질 때 | base rule(`agent-principles` Record Engineering Decisions)이 트리거 — 같은 절차 |

## 7. 안티패턴 (실사례)

| 패턴 | 왜 문제인가 | 대신 |
|---|---|---|
| 초기 설정에서 언어·라이브러리·도구마다 ADR 하나씩 | 빈약한 ADR이 수십 개 쌓여 중요한 결정이 묻힌다 | TRD §2 표 행. 관문 통과한 것만 묶어서 ADR |
| 브랜드 모티프·비주얼 톤·모션 연출을 ADR로 | 아키텍처 결정이 아니다(관문 A) | VISUAL.md. 구현 수단만 TRD §2.1 |
| "도구 X를 쓰지 않는다"(Storybook 등) ADR | 되돌리기 쉽다(관문 B) | TRD §8 개발 기반 한 줄 |
| Rationale "사용자 결정. 유지 비용 절감" | 이유가 없어 나중에 판단 근거가 되지 못한다 | 어떤 제약·우선순위 때문인지 적거나, 못 적으면 ADR 아님 |
| 대안 표에 채택안 행 + 기각 이유 "Rationale 참고" | 칸만 채운 형식 — 정보 0 | 기각한 대안과 실제 기각 이유만 |
| Decision에 폴더 표·import 금지 목록·설정 전문 | 100줄 넘는 ADR, 규칙이 두 곳에서 drift | 실행 규칙은 TRD §3.1·convention, ADR은 골자+링크 |
| Consequences에 rename 범위·수정할 파일 목록 | PR이 이미 담는 내용 | 감수하는 구조적 비용만 |
