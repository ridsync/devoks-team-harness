# ADR (Architecture Decision Record) 작성 규칙 (SSOT)

> 이후 코드 작성 방식을 구속하는 **엔지니어링 결정**을 저장소에 한 결정당 파일 하나로 남긴다.
> 이 문서가 대상 판정·형식·위치·상태 전이의 단일 기준이다. 결정이 나오는 스킬(TRD·FRD·리팩토링·PLAN 실행)은 규칙을 다시 쓰지 않고 이 문서를 가리킨다.

## 1. 대상 판정 — How만, What은 아니다

ADR은 **어떻게 만들고 유지할지(How)** 에 대한 결정만 다룬다. **무엇을 만들지(What)** 는 PRD·FRD가, 일회성 수정은 PR·커밋이 이미 담는다.

| 구분 | 예 | 기록 위치 |
|---|---|---|
| 제품·도메인 결정 (What) | 환불 7일 이내만, 비회원 주문 허용, MVP에서 알림 제외 | PRD §13 / FRD |
| **엔지니어링 결정 (How)** | 상태관리·라이브러리 채택, 모노레포·디렉토리 구조, API 규약, 인증 방식, 캐싱·저장 전략, 테스트 전략 | **ADR** |
| 세부 구현·버그 수정 | null 체크, 쿼리 조건 수정, 기존 패턴 그대로 적용한 설계 | PR·커밋 / FRD `DSN` |

How 결정 중에서도 아래 신호가 **하나 이상** 있을 때만 ADR로 남긴다(정성 기준 — 파일 수 같은 정량 지표로 판정하지 않는다).

1. **되돌리는 비용이 크다** — 데이터 형태·공개 계약·의존성·배포 구조처럼 나중에 바꾸면 이주가 필요하다.
2. **둘 이상의 모듈·기능에 파급된다** — 이 결정이 바뀌면 여러 곳이 같이 바뀐다.
3. **실재한 대안을 비교했다** — 기각한 안이 있었고 그 이유가 코드만으로는 드러나지 않는다.
4. **나중에 "왜 이렇게 했지?"가 나올 결정이다** — 관례와 다르거나 직관에 반한다.

**회색 지대 — ADR로 올린다**
- **도메인 규칙이 기술 구조를 고정할 때**: 규칙 자체는 PRD에, 그 규칙을 구현하는 구조 선택은 ADR에 두고 서로 링크한다. 예: "주문은 삭제하지 않는다"(PRD) → soft-delete·이력 테이블 채택(ADR), "금액은 원 단위 정수"(PRD) → 금액 타입·정밀도 규약(ADR).
- **버그 수정이 구조적 원인을 드러내 방식을 바꿀 때**: 수정은 PR에, "앞으로 이 방식으로 한다"는 규약만 ADR에. 예: 중복 결제 → idempotency key 전면 도입, 경쟁 상태 → 낙관적 락 정책.

**ADR이 아닌 것** — 도메인 정책, 기능 하나 안에서 끝나는 설계(FRD `DSN`), 기존 패턴을 따른 구현, 버그 수정 자체, 에이전트 작업 선호(메모리), 현재 구조 설명(`ARCHITECTURE.md`·README).

> 오류 비용: 누락은 "왜?"를 잃는 비싼 실수이고 과다 기록은 노이즈다. 그래서 애매하면 **제안**하되, 기록은 사용자 확인 후에 한다(§4) — 과다 제안은 확인 한 번으로 걸러진다.

## 2. 위치·이름

```
docs/decisions/
├─ ADR-001-server-state-tanstack-query.md
├─ ADR-002-monorepo-pnpm-workspaces.md
└─ ...
```

- 파일 하나 = 결정 하나. 이름은 `ADR-NNN-<kebab-slug>.md`(3자리 일련번호). 번호는 실행 시 `ls docs/decisions/` 로 기존 최대값을 확인해 +1 한다(추측 금지). 번호는 재사용하지 않는다.
- 별도 색인 파일을 두지 않는다 — 디렉토리 목록(번호·slug)과 각 파일 frontmatter `status`가 색인이다. 제품 TRD가 있으면 TRD §12가 **TRD가 의존하는 ADR의 색인**(ID·제목·상태·링크)을 겸한다. 본문은 ADR 파일에만 둔다(두 곳에 본문을 쓰면 drift).
- `docs/` 레이아웃 SSOT: `output-location.md`.

## 3. 형식

`../assets/ADR.template.md`를 따른다 — frontmatter(`id`·`title`·`status`·`date`·`supersedes`·`superseded_by`·`source`) + `Context` / `Decision` / `Rationale` / `Considered Alternatives` / `Consequences` / `Revisit Conditions` / `Related`. 섹션 제목은 영어로 고정하고(헤더 구조를 바꾸지 않는다), 본문과 `Consequences` 하위 항목은 한국어로 쓴다.

- **Decision**은 "~로 한다" 형태로 한두 문장. 검토 중이면 ADR이 아니라 오픈 이슈(TRD §11·FRD §10)다.
- **Rationale**은 채택 이유를 Context의 요구·제약(NFR-n·불변식·기존 구조)에 연결해 쓴다. 대안별 기각 이유는 `Considered Alternatives` 표에 두고 여기서 반복하지 않는다.
- **대안**은 실제로 비교한 것만. 비교 없이 정했으면 대안 행 대신 "대안 비교 없음 — <이유>"라고 적는다(꾸며 넣지 않는다).
- 버전·지원 여부·가격 같은 시점 의존 사실은 출처(공식 문서 링크)를 붙이고, 확인 못 했으면 `미확정`.
- 날짜는 실행 시 `date +%Y-%m-%d`로 구한다.

## 4. 작성 절차 — 제안 → 확인 → 기록

1. **알아차림** — 작업 중 §1 신호가 있는 결정이 나오면 그 자리에서 "ADR 대상"으로 표시한다.
2. **제안** — 결정·대안·이유를 한 메시지에 담아 "ADR-NNN으로 남길까요?"를 묻는다. 다른 확인 질문과 같은 메시지로 묶는다(확인을 늘리지 않는다).
3. **기록** — 확인되면 `status: accepted`로 파일을 쓴다. 사용자가 거절하면 쓰지 않는다.
4. **비-HITL**(오케스트레이터·서브에이전트 경로) — 묻지 않는다. 결정이 확정 산출물(예: TRD 제안값)의 일부면 `status: proposed`로 쓰고 보고의 확인 목록에 올린다. 그 밖에는 쓰지 않고 "ADR 후보"로 보고만 한다. `accepted`는 사용자 확인 후에만 붙인다.
5. 서브에이전트(`code-implementer` 등)는 ADR을 쓰지 않는다 — 결정이 필요하면 리포트로 올리고 메인 루프가 이 절차를 밟는다.

## 5. 불변성·상태 전이

- `proposed` → `accepted`(확인됨) → `superseded`(새 ADR로 대체) 또는 `deprecated`(대체 없이 폐기).
- `accepted` 이후 본문은 고치지 않는다(오탈자·링크 정정만). 결정이 바뀌면 **새 ADR**을 쓰고 `supersedes: ADR-old`, 기존 파일은 `status: superseded`·`superseded_by: ADR-new`만 바꾼다. 지우지 않는다.
- 현재 구조 설명(`ARCHITECTURE.md` 등)은 계속 고쳐 쓰는 스냅샷이고 ADR은 이유의 이력이다 — 서로 링크만 건다.

## 6. 작성 지점 (스킬별)

| 지점 | 언제 | 처리 |
|---|---|---|
| `product-trd-author` | 스택·구성·인증·저장소·UI 기반 등 §2~§6 판단 확정 시 | 판단마다 ADR 파일, TRD §12에 색인 행 |
| `feature-frd-author`·`feature-workflow-runner` (FRD §4) | `DSN`이 §1 신호를 가질 때(기능 밖으로 파급·되돌리기 어려움) | ADR로 **승격** — DSN 근거 칸에 `ADR-NNN` 기재, 본문은 ADR에 |
| `code-refactoring` | 계획에 구조 방향 전환(계층 재편·의존 방향·패턴 교체)이 있을 때 | 계획 승인 메시지에서 함께 제안 |
| `feature-plan-executor` | 구현 중 PLAN에 없던 결정(새 의존성·구조 변경)이 생겼을 때 | 마무리 보고에 "ADR 후보"로 올리고 확인 후 기록 |
| 그 밖의 작업 | 스킬 밖 대화에서 위 결정이 내려질 때 | base rule(`agent-principles` Record Engineering Decisions)이 트리거 — 같은 절차 |
