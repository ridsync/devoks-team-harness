# AC 리뷰 체크포인트 — 작성한 AC를 사용자가 보고 승인하는 지점

> `feature-frd-author` 절차 7의 상세 SSOT. AC는 Contract·Edge·화면 상태에서 파생되므로 작성 **전에** 묻지 않는다. 초안을 보여 주고 고치게 한다.
> 오류 비용이 비대칭이다 — AC가 틀린 채 PLAN·구현까지 가면 재작업이 크고, 표 한 장 리뷰는 싸다.

## 언제

- 절차 3(EARS 정형화)이 끝나 AC 초안이 있고, `FRD.md`를 쓰기 **전**.
- 슬롯·정책 질문과 Success·Non-goals 제안값이 있으면 **같은 턴에** 함께 보여 준다(확인 왕복을 늘리지 않는다). §4 설계안 제안·확인이 따로 있는 복잡 기능만 AC 리뷰를 설계안 확인 뒤 **별도 메시지**로 한다(설계 판단과 요구 판단을 섞지 않는다).
- **개수로 메시지를 나누거나 페이지를 쪼개지 않는다.** 리뷰가 어려운 것은 분량이 아니라 구조 없이 나열됐을 때다 — 아래 "표 형식"의 REQ 요약표(지도)와 REQ 단위 응답으로 푼다. 불필요한 분할은 왕복만 늘린다.
- **REQ 단위로 응답할 수 있다** — "REQ-003만 고치고 나머지 승인"처럼 부분 수정을 받는다. 승인은 전체 AC에 대해 한 번이다.
- **FRD 분리는 AC 리뷰에서 다루지 않는다** — 요구 추출 단계(frd-author 절차 2)에서 판단한다. AC가 많다는 이유만으로 분리를 제안하지 않는다(REQ가 크고 REQ 수는 적은 경우 처방이 틀린다).

## 표 형식 — EARS 한 가지로

AC는 **`FRD.md`에 저장될 EARS 문장 그대로** 보여 준다. 본문은 이미 한국어(키워드 `WHEN/IF/WHILE/THE SYSTEM SHALL`만 영어)라 풀이를 따로 붙이지 않는다 — 같은 내용을 워딩만 달리 두 번 보이면 어느 쪽이 기준인지 헷갈린다. 사용자가 승인한 문장이 곧 저장되는 문장이다.

먼저 **REQ 요약표**(지도, 4~13행)를 보여 주고, 이어 REQ별로 AC를 나열한다. AC 줄 끝에 `[검증 방법 · Success]` 태그만 붙인다.

| REQ | 제목 | AC (정상/예외) | 검증 방법 분포 | Success |
|-----|------|----------------|----------------|---------|
| REQ-001 | 저장한 뷰 적용 | 3 (2/1) | 테스트 코드 3 | S1 |

REQ별 AC:

**REQ-001 — 저장한 뷰 적용**
- `AC-001-1` WHEN 사용자가 저장된 뷰를 선택 THE SYSTEM SHALL 해당 뷰의 필터 조합을 목록에 즉시 적용한다. `[테스트 코드 · S1]`
- `AC-001-3` IF 저장된 뷰의 필터 키가 현재 스키마에 없으면 THEN THE SYSTEM SHALL 해당 키를 무시하고 경고 토스트를 노출한다. `[테스트 코드 · —]`

- **검증 방법 값 4종** — `테스트 코드`(구현 중 작성·수정한 단위·통합·E2E 테스트로 확인 — 코드로 남아 다시 실행된다) / `에이전트 확인`(에이전트가 실행 중인 앱을 조작해 UI 상태+영속 상태를 확인, 코드는 남지 않음 — `devoks-sdlc:verify-acceptance-test`) / `사람 확인`(사람이 직접 확인 — 자동화 불가·`verify-acceptance-test` 미지원 환경(모바일 네이티브 등)) / `출시 후 계측`(KPI·로그·트레이스 등 운영 측정으로만 판정). 기본값은 스킬이 제안하고 사용자는 틀린 것만 고친다.
- **Success 연결** — §1 Success 항목에 `S1`·`S2`…를 붙이고, 그 Success를 증명하는 AC·CTR을 가리킨다. 연결 AC가 없는 Success는 표 아래에 "연결 불가: <S-n> — 사유(예: 출시 후 측정)"로 적고 §10에도 남긴다. 어떤 Success에도 연결되지 않는 AC는 `—`로 두되 삭제하지 않는다(사용자가 원한 것일 수 있다).
- 끝에 §1 Non-goals를 한 줄로 다시 보여 준다 — "만들지 않을 것"은 AC 리뷰에서 가장 자주 어긋난다.
- "이대로 승인하시면 FRD를 확정합니다. 고칠 AC가 있으면 번호로 말씀해 주세요."로 닫는다.

## 승인 규칙

- 통과는 명시 표현("네"·"맞아요"·"승인")뿐이다. 수정이 오면 반영해 표를 다시 보여 준다. 침묵·"알아서"는 승인이 아니다.
- **HITL** — 명시 승인 뒤 `FRD.md`를 쓰고 frontmatter `status: approved`로 둔다. 승인된 표의 "검증 방법"은 §9 "AC별 검증 방법" 표로 옮긴다.
- **비-HITL**(서브에이전트·`/loop`·자동 파이프라인) — 묻지 않는다. `status: review`로 쓰고 완료 보고에 "AC 사용자 미검토"를 남긴다. 다음 단계(PLAN 작성)가 `review → approved`로 올릴 때 PLAN §1에도 같은 한 줄을 남긴다. 파이프라인은 막지 않는다.
- 사용자가 리뷰를 보류하면(나중에 보겠다) `status: review`로 두고 §10에 "AC 리뷰 보류"를 적는다 — 비-HITL과 같이 PLAN 단계에서 미검토 한 줄이 남는다.
