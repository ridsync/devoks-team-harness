# AC 리뷰 체크포인트 — 작성한 AC를 사용자가 보고 승인하는 지점

> `feature-frd-author` 절차 7의 상세 SSOT. FRD §3 AC는 EARS 문장이라 사용자가 추상적으로 답하기 어렵고,
> AC는 Contract·Edge·화면 상태에서 파생되므로 작성 **전에** 묻지 않는다. 초안을 보여 주고 고치게 한다.
> 오류 비용이 비대칭이다 — AC가 틀린 채 PLAN·구현까지 가면 재작업이 크고, 표 한 장 리뷰는 싸다.

## 언제

- 절차 3(EARS 정형화)이 끝나 AC 초안이 있고, `FRD.md`를 쓰기 **전**.
- **분량으로 메시지를 나눈다** — AC가 **20개 이하**면 슬롯·정책 질문과 Success·Non-goals 제안값을 **같은 메시지**에 함께 보여 준다(확인 왕복을 늘리지 않는다). **20개 초과**면 슬롯·정책 확인을 먼저 끝내고 AC 리뷰를 **별도 메시지**로 한다. **40개 초과**면 REQ 묶음 단위로 쪼개 페이지마다 승인받는다(한 페이지 AC 약 15~20개, REQ는 쪼개지 않는다).
  - 이유: 기존 FRD 22건 실측에서 AC는 중앙값 약 27개(최소 11·최대 82)였다. 한 메시지에 슬롯 질문과 AC 수십 개가 섞이면 사용자는 훑고 "네"만 하게 된다(도장 승인). 기준을 낮게 잡아 분리가 잦아도 비용은 왕복 한 번이고, 못 잡으면 AC 리뷰가 형식이 된다 — 오류 비용이 비대칭이라 정량 기준을 쓴다.
- §4 설계안 제안·확인이 따로 있는 복잡 기능도 AC 표는 설계안 확인 뒤 별도 메시지다(설계 판단과 요구 판단을 섞지 않는다).
- AC가 40개를 넘는 FRD는 기능이 너무 크다는 신호이기도 하다 — 리뷰 전에 FRD를 REQ 묶음 단위로 나눌지 한 줄로 제안한다(강제 아님).

## 표 형식 — EARS 원문 + 한국어 풀이

AC는 **EARS 원문과 한국어 풀이를 함께** 보여 준다. 원문만 있으면 비개발자가 판단하기 어렵고, 풀이만 있으면 `FRD.md`에 저장될 문장과 사용자가 승인한 문장이 달라진다. **`FRD.md`에는 EARS 원문만 기존 양식 그대로 저장**한다(풀이는 리뷰용이며 저장하지 않는다).

먼저 **REQ 요약표**(지도, 4~13행)를 보여 주고, 이어 REQ별로 AC를 나열한다.

| REQ | 한 줄 풀이 | AC (정상/예외) | 검증 방법 분포 | Success |
|-----|------------|----------------|----------------|---------|
| REQ-001 | 저장한 뷰를 적용한다 | 3 (2/1) | 자동 3 | S1 |

REQ별 AC:

**REQ-001 — 저장한 뷰를 적용한다**
- `AC-001-1` WHEN 사용자가 저장된 뷰를 선택 THE SYSTEM SHALL 해당 뷰의 필터 조합을 목록에 즉시 적용한다.
  → 저장한 뷰를 누르면 목록에 바로 반영된다. · 자동테스트 · S1
- `AC-001-3` IF 저장된 뷰의 필터 키가 현재 스키마에 없으면 THEN THE SYSTEM SHALL 해당 키를 무시하고 경고 토스트를 노출한다.
  → 없어진 필터 키는 무시하고 경고만 뜬다. · 자동테스트 · —

- **검증 방법 값 4종** — `자동테스트`(단위·통합) / `실동작`(UI 조작+상태 영속을 실행 중인 앱에서 확인 — `devoks-sdlc:verify-acceptance-test`) / `수동`(자동화 불가·모바일 네이티브 등) / `출시 후 계측`(출시 후 실측으로만 판정). 기본값은 스킬이 제안하고 사용자는 틀린 것만 고친다.
- **Success 연결** — §1 Success 항목에 `S1`·`S2`…를 붙이고, 그 Success를 증명하는 AC·CTR을 가리킨다. 연결 AC가 없는 Success는 표 아래에 "연결 불가: <S-n> — 사유(예: 출시 후 측정)"로 적고 §10에도 남긴다. 어떤 Success에도 연결되지 않는 AC는 `—`로 두되 삭제하지 않는다(사용자가 원한 것일 수 있다).
- 끝에 §1 Non-goals를 한 줄로 다시 보여 준다 — "만들지 않을 것"은 AC 리뷰에서 가장 자주 어긋난다.
- "이대로 승인하시면 FRD를 확정합니다. 고칠 AC가 있으면 번호로 말씀해 주세요."로 닫는다.

## 승인 규칙

- 통과는 명시 표현("네"·"맞아요"·"승인")뿐이다. 수정이 오면 반영해 표를 다시 보여 준다. 침묵·"알아서"는 승인이 아니다.
- **HITL** — 명시 승인 뒤 `FRD.md`를 쓰고 frontmatter `status: approved`로 둔다. 승인된 표의 "검증 방법"은 §9 "AC별 검증 방법" 표로 옮긴다.
- **비-HITL**(서브에이전트·`/loop`·자동 파이프라인) — 묻지 않는다. `status: review`로 쓰고 완료 보고에 "AC 사용자 미검토"를 남긴다. 다음 단계(PLAN 작성)가 `review → approved`로 올릴 때 PLAN §1에도 같은 한 줄을 남긴다. 파이프라인은 막지 않는다.
- 사용자가 리뷰를 보류하면(나중에 보겠다) `status: review`로 두고 §10에 "AC 리뷰 보류"를 적는다 — 비-HITL과 같이 PLAN 단계에서 미검토 한 줄이 남는다.
