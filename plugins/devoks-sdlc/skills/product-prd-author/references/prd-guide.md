## 1. 착수 점검 7문항 ↔ PRD 섹션

입력 양식 `assets/PRD.intake.md`가 이 7문항의 SSOT 형식이다(★ 1·7번 필수 — 1번이 비면 인터뷰, 7번만 비면 제안 후 확인). 각 문항에 한두 문장으로 답할 수 있으면 해당 섹션을 쓸 수 있다. 판정: **확정**(입력에 명시) / **부분**(추론 가능하나 확인 필요) / **미확정**(근거 없음).

| # | 질문 | 채우는 섹션 | 흔한 "부분" 상태 |
|---|---|---|---|
| 1 | 이 제품은 **누구의 어떤 문제**를 푸는가? | §1, §2 | 사용자가 "모두"이거나 문제가 솔루션으로 서술됨 |
| 2 | 그 사람은 **지금 어떻게** 해결하고 있는가? | §2 현재 해결 방식, §3 대안 | 현재 방식이 언급되지 않음 |
| 3 | 대안과 비교해 우리는 **무엇이 다른가**? | §3 | 기능 나열만 있고 "아무것도 안 함" 대비 이유가 없음 |
| 4 | 성공을 **어떤 숫자**로 아는가? | §4 | 목표는 있으나 지표 이름이 없음 — **지표 이름이 정해지면 확정**(목표치는 출시 후) |
| 5 | **절대 넘을 수 없는 제약**은? | §7 | 일정만 있고 플랫폼·연동·법규 미언급 |
| 6 | **가장 불확실한 가정**은 무엇이고 확인했는가? | §9 | 가정이 사실처럼 서술됨 |
| 7 | 첫 버전에서 **하지 않을 것**은? | §8 | 거의 항상 비어 있음 — 입력에서 제외 후보를 제안하고 일괄 확인한다(★, 미확정으로 남기지 않는다) |

판정표 예시:

```
| # | 판정 | 근거 (원문) | 예상 답 (확인 필요 시) |
|---|---|---|---|
| 1 | 확정 | "소규모 필라테스 센터 원장이 수기로 예약을 관리" | — |
| 4 | 미확정 | 언급 없음 | 월 노쇼율로 보면 될까요? (현재 수치가 있으면 기준값으로) |
| 7 | 부분 | "결제는 나중에" | 온라인 결제는 MVP 제외, 다음 버전 — 맞나요? |
```

수익화가 MVP에 포함되면 "무엇에, 언제 돈을 내는가"를 §3에 함께 확정한다 — 결제·업그레이드 흐름이 MVP 범위에 들어오기 때문이다.

## 2. 작성 규칙

**① 문제로 시작해 문제로 검증한다.** 모든 FR은 G 또는 S로 역추적된다. 연결이 안 되는 FR은 삭제 후보로 보고한다(임의 삭제 금지 — 사용자가 원한 것일 수 있다).

**② What·Why만.** 솔루션 지정은 탐색 공간을 닫는다.

| 입력 문장 | PRD 문장 |
|---|---|
| 하단 탭 3개로 구성 | 사용자는 예약·회원·정산 세 과업 사이를 한 번에 전환할 수 있다 |
| Firebase로 푸시 | 시스템은 예약 1시간 전 회원에게 알림을 보내야 한다 (+ 기술 선택은 TRD로) |
| 관리자 대시보드 | 원장은 오늘의 예약·빈 슬롯을 한 화면에서 확인할 수 있다 |

입력이 기술을 **제약으로** 지정했다면(예: "기존 사내 SSO 필수") §7 제약에 그대로 쓴다.

**③ 측정 불가 형용사·모호어를 숫자로.** 스캔 대상 예: 빠르게, 간편한, 직관적인, 매끄러운, 쉽게, 많은, 대부분, 적절한, 지원한다, 등. "빠르게" → "주요 화면 응답 1초 이내"; 근거 숫자가 없으면 `미확정 (제안: 1초 — 일반적인 모바일 체감 기준)`처럼 두고 §11에 확인 항목을 올린다(⑦ 참고).

**④ 근거 없는 주장은 가정으로.** "사용자들은 X를 원한다"의 근거가 입력에 없으면 §9 `A-n`(유형·검증 방법)으로 옮긴다.

**⑤ 비목표가 목표만큼 중요하다.** Out of Scope에는 이유와 행선지(다음 버전/영구 제외)를 함께 적는다 — 이유가 없으면 회의마다 다시 논쟁이 된다.

**⑥ 짧을수록 읽힌다.** 본문은 표·불릿 위주, 상세 근거는 링크. 기준: 섹션당 한 화면 이내, 전체 FR 30개를 넘으면 FR 단위가 너무 잘게 쪼개진 신호(그건 FRD 해상도다).

**⑦ 사실은 지어내지 않고, 판단은 표시해서 제안한다.**

| 구분 | 예 | 입력에 없을 때 |
|---|---|---|
| 사실 (관측·합의된 값) | KPI 기준값(현재 수치), 일정·인력·예산, 경쟁 제품명, 법적 요건 | `미확정` — 제안 금지. 제안하면 측정되지 않은 현재를 꾸며내게 된다 |
| 판단 (빌드에 영향) | NFR 수치, 정책(취소 기한 등), Out of Scope 후보, 우선순위 | `미확정 (제안: <값> — <근거 한 줄>)` 가능 |
| 출시 후 측정 | KPI 목표치·판정 기준·중단 기준 | 쓰지 않는다 — ⑧ |

- 근거는 입력에서 끌어낸 추론이나 흔한 업계 관행 한 줄이면 된다("메신저 문의 대체가 목표 → 사용 첫 분기 50% 감소를 출발점으로"). 근거를 댈 수 없으면 제안하지 않는다.
- 제안값은 확정값처럼 보이면 안 된다 — 항상 `미확정 (제안: …)` 형태 그대로 두고, §11에 "제안값 확인" 항목으로 올린다.
- 사용자가 확인하면 갱신 모드에서 `(제안: …)`을 걷어내고 확정값으로 바꾼다(patch).

**⑧ KPI는 측정 수단까지만 — 목표치는 출시 후.** KPI는 작업 완료(DoD)와 무관하고 출시 후 실측으로 채운다. 그래도 개발 중에 만들어야 하는 파생물이 둘 있다.

| 파생물 | 왜 개발 범위인가 | 처리 |
|---|---|---|
| 계측 | 데이터를 남기지 않으면 출시 후 측정 자체가 불가능 | 지표마다 "측정에 필요한 데이터"를 적고 계측 FR/NFR로 내린다 (예: `FR-n 시스템은 예약 생성·취소를 시각·경로와 함께 기록해야 한다`) |
| 제품 불변식 | "이중 예약 0건"처럼 빌드 시 테스트로 보장할 수 있는 가드레일은 지표가 아니라 규칙 | §7 `NFR-n`으로 올리고 §4에서는 ID만 참조 |

- 입력이 목표치를 이미 줬다면("문의 50% 감소") §1 근거나 §4 지표 설명에 원문으로 남긴다 — 지어내지 않되 버리지도 않는다.
- 측정값을 채우는 것은 출시 후 갱신 모드 몫이다(minor).

## 3. 자체 점검 체크리스트

- [ ] 개요 한 문단이 §1~§4와 모순되지 않는다.
- [ ] 모든 FR → G/S 근거가 있다. 모든 G → 최소 하나의 FR(MVP 목표면 MVP FR)이 있다.
- [ ] 핵심 KPI가 1개다(여러 개면 하나를 핵심으로, 나머지는 보조로). 지표마다 계측 FR/NFR이 연결돼 있다.
- [ ] 목표치·기한·중단 기준 칸이 없다. 빌드 시 검증 가능한 가드레일은 §7 NFR로 올라가 있다.
- [ ] 담당·기한·일정 같은 운영 정보 칸이 없다. FRD 시드는 PRD 미확정을 다시 적지 않고 Q-n ID로 참조한다.
- [ ] 모호어 스캔 결과 남은 것이 없다(남으면 미확정+§11).
- [ ] FR에 화면·컴포넌트·기술 지정이 없다. EARS AC·상태별 화면 정의가 없다.
- [ ] Out of Scope 최소 1개, 각각 이유+행선지.
- [ ] §9 가정마다 유형·검증 방법이 있다. 위험도 "상"은 §10 MVP에서 검증 경로가 있다.
- [ ] 본문의 모든 "미확정"(제안값 포함)이 §11에 대응한다. 관련 미확정은 한 항목으로 묶어도 된다(예: "NFR 수치 제안값 확인").
- [ ] 기준값·일정·인력·예산 칸에 제안값이 없다(사실 칸). 제안값에는 근거 한 줄이 붙어 있다.
- [ ] FEATURES.md: 모든 FR이 정확히 한 F에 속하고, 각 F에 FRD 시드(`## 기능 정련 요약` 헤더 + ★ Outcome·User·Success·Out of scope)가 있다. 의존 순서가 릴리스 순서와 모순되지 않는다.

## 4. 갱신 모드 — 버전·이력 규칙

| bump | 기준 | 예 |
|---|---|---|
| major | 문제·주 타깃·핵심 KPI가 바뀜 (제품 재정의) | B2C → B2B 전환, 핵심 KPI 교체 |
| minor | 범위·목표·FR·NFR·마일스톤의 추가/삭제/우선순위 변경 | FR 추가, MVP에서 기능 제외, 가정 검증 결과로 방향 수정 |
| patch | 의미 불변 정정 | 문구 정리, 오타, 링크, 미확정 → 확정 값 채움(범위 불변일 때) |
| minor | 출시 후 측정 결과 반영 | §4 지표에 실측값·목표 판정 기록, 그 결과로 범위 조정 |

- 이력 행 형식: `| 0.3.0 | 2026-11-02 | FR-7 추가, F-4 MVP→Next | A-2 검증 실패(노쇼 알림 수요 낮음) — 원장 합의 |`
- 결정 로그는 별도 파일 없이 이 표의 "사유·결정" 열이다. "왜 이렇게 정했지?"에 답할 수 있게 근거(데이터·회의·사람)를 짧게라도 남긴다.
- `dropped` 처리: FR/F 행을 지우지 않고 상태·릴리스 열에 `dropped (v0.3.0: 사유)`.
- `FEATURES.md` frontmatter `prd_version`을 PRD 버전과 맞춘다.
- `status: approved` 상태에서 minor 이상 변경이 생기면 `review`로 되돌릴지 사용자에게 묻는다.

## 5. 문서 경계 (PRD / FRD / TRD)

| 내용 | PRD | FRD (`feature-frd-author`) | TRD (`product-trd-author`) |
|---|---|---|---|
| 문제·타깃·가치·제품 KPI | ● | 참조 | |
| 기능 목록·우선순위·릴리스 | ● (FR·F) | | |
| 기능별 Success·Non-goals | 시드 | ● | |
| EARS AC · Contract · Edge · 화면 상태 | ✕ | ● | |
| 공통 NFR | ● (NFR-n) | 참조·구체화 | 구현 방식 |
| 아키텍처·데이터 모델·기술 선택 | ✕ (제약만) | §4 설계(기능 범위) | ● |

경계가 애매하면 두 질문을 차례로 쓴다: ① "무엇·왜(요구)인가, 어떻게(기술)인가?" → 어떻게면 TRD 쪽. ② "이 문장이 바뀌면 여러 기능이 같이 바뀌는가?" → 그렇다면 PRD(요구) / TRD(기술), 한 기능만이면 FRD.
