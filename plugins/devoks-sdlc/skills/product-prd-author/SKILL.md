# product-prd-author — 제품 PRD · 기능 백로그 작성/갱신

장기 프로젝트에서 "무엇을 왜 만드는가, 무엇이 성공인가, 무엇을 하지 않는가"를 고정하는 **제품 단위 SSOT**를 만든다.
기능 하나의 상세(EARS AC·Contract·Edge·화면 상태)는 FRD가 소유하므로 PRD에 쓰지 않는다 — 두 문서에 같은 내용이
있으면 장기 프로젝트에서 반드시 어긋난다. PRD는 기능 백로그(`FEATURES.md`)로 끝나고, 백로그 항목 하나가 FRD 하나의 입력이 된다.

```
아이디어 ─▶ product-interview ─┐
채운 PRD.intake.md·기획서 ──────┴▶ [이 스킬] PRD.md + FEATURES.md ─▶ (항목별) feature-frd-author ─▶ plan ─▶ execute
```

## 범위 (중요)

| 입력 | 쓸 스킬 |
|---|---|
| 제품·서비스 전체, 여러 기능으로 이뤄진 장기 프로젝트 (채운 입력 양식·기획서) | **이 스킬** |
| 제품 아이디어만 있음, 대화로 정리부터 | `devoks-sdlc:product-interview` → 승인 후 이 스킬로 자동 연결 |
| 입력 양식만 필요 | **이 스킬** (양식 요청 — 아래) |
| 이미 있는 PRD에 범위·목표·결정 변경 반영 | **이 스킬** (갱신 모드) |
| 기능 하나의 요구서 | `devoks-sdlc:feature-frd-author` (백로그의 FRD 시드를 초안으로) |
| 기능 하나의 의도가 막연함 | `devoks-sdlc:feature-interview` |

- 하지 않는 것: 기능별 EARS AC·Contract·Edge, 화면 설계·와이어프레임, 기술 설계(TRD·아키텍처), 작업 분해, 코드 작성.
- 시장 규모 추정·경쟁사 심층 조사는 하지 않는다. 대안 비교는 "사용자가 지금 쓰는 것 대비 무엇이 다른가"까지만.

## 호출 방법

```
/devoks-sdlc:product-prd-author [src=<아이디어 본문|요구 문서 경로> (default: 대화 맥락)] [out=<디렉터리> (default: docs/product)]
```

> 표기: `key=값` 필수 · `[key=값]` 선택 · `(default: X)` 미지정 시 X로 진행.

- 산출물: `<out>/PRD.md`, `<out>/FEATURES.md`. 장기 문서라 일회성 워크스페이스(`.claude/workspace/`)가 아니라 저장소에 남는 경로를 쓴다.
- `<out>/PRD.md`가 이미 있으면 **갱신 모드**로 동작한다(덮어쓰지 않는다).

### 양식만 요청받은 경우

"PRD 양식 줘"처럼 입력 양식만 원하면 `assets/PRD.intake.md`를 `<out>/PRD.intake.md`로 복사하고(이미 있으면 덮어쓰지 않고 경로만 알린다) 채우는 방법 한 줄 — "채운 뒤 `/devoks-sdlc:product-prd-author src=<out>/PRD.intake.md`" — 을 안내하고 멈춘다. PRD는 쓰지 않는다.

## 절차

### 0. 입력 수집 · 모드 판별

- `src`(파일이면 전부 읽는다)와 대화 맥락에서 원문을 모은다. 입력 원문은 `<out>/sources/`에 사본(또는 저장소 내 경로)으로 남겨 근거를 추적할 수 있게 한다.
- 저장소 안이면 README·기존 docs·코드 구조를 가볍게 훑어 기존 시스템·플랫폼·연동 같은 **제약의 근거**로만 쓴다(설계 제안 금지).
- `<out>/PRD.md` 존재 → 갱신 모드(아래 "갱신 모드"로). 없으면 신규 작성.

### 1. 입력 게이트 — 착수 점검 7문항

입력의 형식은 `assets/PRD.intake.md`(7문항)가 SSOT다. 입력이 `## 제품 정련 요약`(채운 양식 또는 `product-interview`의 승인된 요약)이면 그 값은 다시 묻지 않는다. 그 밖의 기획서·메모는 `references/prd-guide.md` §1 기준으로 7문항에 대조해 각 항목을 **확정 / 부분 / 미확정**으로 판정하고, 근거(원문 인용 한 줄)를 붙여 표로 보여준다.

- **★ 1번(누구의 어떤 문제)이 부분·미확정이거나 무엇을 만들지 방향이 갈리면** 슬롯 질문으로 메우지 않고 Skill 도구로 `devoks-sdlc:product-interview`에 진입한다(그 스킬 절차를 이 흐름 안에서 수행). 승인된 요약이 돌아오면 그것을 입력으로 이어간다 — 대상과 문제는 PRD의 방향 자체라 대화로 좁혀야 한다. 사용자가 인터뷰를 원치 않으면 아래 일괄 확인으로 진행한다.
- **★ 7번(하지 않을 것)만 비었으면** 인터뷰하지 않는다. 입력에서 추론한 제외 후보를 `제안: <항목> — <이유> — <행선지>`로 만들어 아래 일괄 확인에 함께 올린다. ★7은 미확정으로 남길 수 없으므로 사용자가 제안을 받아들이거나 고친 값으로 확정한다 — 사용자 입력은 대개 불완전하니, 고칠 대상을 먼저 보여 주는 쪽이 질문보다 빠르다.
- 나머지 부분·미확정 항목은 **한 메시지에 모아** 묻는다. 각 질문에 입력에서 추론한 **예상 답**을 붙여 사용자가 "맞다/아니다"로 빠르게 답할 수 있게 한다. 제품 수준 질문은 많아서 하나씩 물으면 대화가 지나치게 길어진다.
- 사용자가 답하지 않거나 "모르겠다"인 칸은 **"미확정"**으로 두고 진행한다 — 비워 두거나 지어내는 것보다 낫다. 미확정은 §11 오픈 이슈로 모인다.
- **비-HITL 맥락**(서브에이전트 위임, `/loop`, 자동 파이프라인)에서는 묻지도 인터뷰로 진입하지도 않는다. 확정되지 않은 칸은 전부 "미확정"으로 쓰고, ★ 1·7번이 미확정이면 보고 첫머리에 "★ 미확정 — 사람 확인 전 FRD 착수 보류"를 blocker로 남긴다.

### 2. PRD.md 작성

`assets/PRD.template.md` 골격을 따른다(헤더 구조를 바꾸지 않는다 — 갱신 모드와 다음 단계가 이 구조를 파싱한다). 작성 규칙은 `references/prd-guide.md` §2.

- **What·Why만, How 금지** — "탭 3개로 구성" 같은 솔루션 문장은 사용자 니즈로 되돌린다("3개 과업을 오가며 처리해야 한다"). 단 기술·법규·브랜드 제약은 §7에 분명히 쓴다.
- **근거 없는 주장은 가정으로 내린다** — "사용자들은 원한다"에 근거가 없으면 §9 가정(`A-n`)으로 옮기고 검증 방법을 붙인다.
- **측정 불가 형용사 금지** — "빠르게·간편한·직관적인"은 숫자·경계 조건으로 바꾸고, 바꿀 근거가 없으면 "미확정"과 함께 §11로.
- 기능 요구(`FR-n`)는 **능력 단위**("사용자는 ~할 수 있다") + MoSCoW + 근거(`G-n`/`S-n`)까지만. AC·화면 상태·에러 처리는 쓰지 않는다(FRD 몫).
- 여러 기능에 걸치는 NFR(성능·보안·접근성·오프라인 등)은 §7에 `NFR-n`으로 **한 번만** 정의한다 — FRD는 이를 참조한다.
- **사실은 지어내지 않고, 빌드에 영향을 주는 판단은 제안할 수 있다.** 기준값(현재 수치)·날짜·인력·예산·경쟁 제품명 같은 사실은 입력에 있을 때만 쓰고, 없으면 "미확정". NFR 수치·정책·Out of Scope 후보처럼 구현을 좌우하는 판단 값은 `미확정 (제안: <값> — <근거 한 줄>)`로 출발점을 줄 수 있고 §11에 올린다. 기준 상세는 `references/prd-guide.md` §2 ⑦.
- **KPI는 측정 수단까지만.** 목표치·판정 기준은 출시 후 측정해 채우는 값이라 쓰지 않는다. 대신 지표마다 필요한 데이터를 계측 FR/NFR로 내리고, 빌드 시 테스트 가능한 가드레일(이중 예약 0건 등)은 §7 NFR로 올린다 — 이 둘은 개발 중에 만들지 않으면 출시 후 측정·보장이 불가능하다. → `references/prd-guide.md` §2 ⑧.
- 담당·기한·일정 같은 사람의 운영 정보는 칸을 두지 않는다. 오픈 이슈는 무엇의 착수를 막는지만 적는다.

### 3. FEATURES.md 작성 (기능 백로그)

`assets/FEATURES.template.md`를 따른다. FRD 시드는 FRD 입력 양식(`../feature-frd-author/assets/FRD.intake.md`)과 같은 칸을 쓴다. `FR`을 사용자가 체감하는 기능 단위 `F-n`으로 묶고, 릴리스(MVP/Next/Later)·의존·상태를 매긴다.
각 항목에 **FRD 시드**를 붙인다 — ★ 칸(Outcome·User·Success·Out of scope)이 `feature-frd-author`의 의도 게이트 슬롯과 같아서, 시드를 초안으로 넘기면 인터뷰 없이 FRD 정련으로 바로 들어갈 수 있다.

### 4. 자체 점검 → 보고

`references/prd-guide.md` §3 체크리스트를 돌린다(역추적·모호어·Out of Scope 이유·미확정 수집·분량). 실패 항목은 고친 뒤 보고한다.

보고에는 다음만 담는다: 산출물 경로, 섹션별 확정/미확정 요약, 미확정·오픈 이슈 목록(디자인·개발 착수를 막는 것 먼저), 다음 단계(신규 개발이거나 여러 기능이 공유할 기술 구조가 필요하면 `/devoks-sdlc:product-trd-author` → 그다음 MVP 백로그 항목 → `/devoks-sdlc:feature-frd-author frd=<FRD 시드 본문>`).
`PRD.md` frontmatter는 `version: 0.1.0`, `status: draft`로 시작한다. `review`·`approved` 전환은 사용자가 명시할 때만 한다.

## 갱신 모드

PRD는 결정이 바뀔 때마다 고쳐야 신뢰가 유지되는 살아있는 문서다. 상세 규칙은 `references/prd-guide.md` §4.

1. 기존 `PRD.md`·`FEATURES.md`를 먼저 읽고, 변경 요청을 섹션 단위 **변경 목록**(추가/수정/삭제 + 영향받는 ID)으로 정리한다.
2. 연쇄 영향을 찾는다 — 목표가 바뀌면 그 목표를 근거로 한 `FR`·KPI, `FR`이 빠지면 그것을 담은 `F-n`.
3. 버전 bump 수준(major/minor/patch)을 제안하고 변경 목록과 함께 **확인을 받은 뒤** 쓴다(비-HITL이면 변경 목록을 보고만 하고 쓰지 않는다). 문제·타깃·핵심 KPI가 바뀌는 major 변경은 사실상 제품 재정의이므로 특히 분명히 짚는다.
4. 반영 후 §13 변경 이력에 `버전 | 날짜 | 변경 요약 | 사유·결정`을 추가한다. 삭제한 FR·F는 지우지 않고 `dropped`로 남기고 사유를 적는다 — 이미 FRD로 넘어간 항목의 추적이 끊기지 않게 하기 위해서다. `FEATURES.md`의 "기반" 구역(B-n)은 `product-trd-author` 소유라 고치지 않는다 — 범위 변경이 기반에 영향을 주면 "TRD 갱신 필요"로 보고한다.
5. 이미 FRD가 연결된(`FEATURES.md` 상태 `frd` 이후) 항목이 영향을 받으면 해당 FRD 경로를 "재검토 필요"로 보고한다(FRD를 직접 고치지 않는다).

## 완료 기준

- 7문항 판정표를 보여줬고(승인된 정련 요약 입력이면 생략), ★ 1·7번은 확정 또는 인터뷰로 채워졌으며, 미확정 칸은 PRD에 "미확정"으로 명시되어 §11에 모였다.
- §1 문제 진술, §4 목표(≤3)·핵심 KPI(지표 이름 + 계측 FR/NFR 연결), §8 Out of Scope(이유+행선지 최소 1개)가 있다.
- 모든 `FR`이 `G`/`S`로 역추적되고, 모든 MVP 목표에 그것을 이루는 `FR`이 있다.
- PRD에 EARS AC·화면 상태·컴포넌트·기술 설계가 없다.
- `FEATURES.md`의 모든 `FR`이 정확히 하나의 `F`에 속하고, 각 `F`에 FRD 시드가 있다.
- 갱신 모드: 사용자 확인 후 반영, 버전 bump, §13 이력 추가, 영향받은 FRD 보고.
