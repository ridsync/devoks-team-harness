# refactoring-execution — 리팩토링 실행 절차 (엔진 SSOT)

**호출 주체:** `devoks-sdlc:code-refactoring` 스킬 본문(메인 루프에서 직접 수행 — 계획-승인-실행 상호작용이
절차의 본질이라 서브에이전트로 위임하지 않는다).
진입 스킬의 Phase 0에서 **대상·목표·제약**이 이미 확정된 상태를 전제한다 — 이 문서 안에서 범위 모호성을
다시 확인하지 않는다.

**이 문서는 절차만 정한다.** 무엇이 위반인지(크기 상한·네이밍·주석·스택 패턴·냄새)는 아래 §2의 기준 문서가
SSOT이며, 이 문서에 값을 다시 적지 않는다 — 스택마다 값과 패턴이 다르고, 두 곳에 적으면 어긋난다.

---

## 2. 현황 파악 (정보 수집)

대상 파일을 읽고, 동작 이해에 필요한 **직접 의존 모듈만 최소 범위로** 추가 탐색한다. 리팩토링 전에 프로젝트가
실행 가능한 상태(테스트·린트·타입 체크 통과 여부)인지 먼저 확인해 기준선을 남긴다.

다음 기준 문서로 위반 항목을 도출한다. 문서가 없거나 해당 절이 비어 있으면 그 기준은 건너뛰고 리포트에 적는다
(기준을 지어내지 않는다).

| 기준 문서 | 볼 것 |
|----------|------|
| `.claude/rules/agent-principles.md` | SSOT·DRY·Fail-Fast·Explicit Handling, [Structure](파일 묶음·배치·공개면), [Code Smells] |
| `.claude/rules/project-convention.md` | Code Size(목표·상한), Naming, Comment Rules, Complexity Gate, 스택 패턴(상태·데이터·에러 처리·로깅·계약 검증), Pitfalls, Project Decisions 구조 슬롯(S1~S8) |
| `.claude/refs/code-review.md` | Layered Examination Level 1~5, §5 Code Smells 신호표(탐지 신호·권장 리팩터링·지적하지 않는 냄새·오탐 가드) |
| `.claude/CLAUDE.md` | 프로젝트 구조·명시된 예외(예: Fail-Fast 예외 경로) |

프로젝트 Complexity Gate lint가 있으면 그 결과를 먼저 수집해 기계로 잡히는 위반은 그것으로 대신한다.

## 3. 리팩토링 계획 수립 및 승인

다음을 정리해 **사용자 승인을 받은 뒤** 코드 변경에 들어간다.

- 수정·생성·삭제 파일 목록
- 문제별 개선 방향 — 위반마다 근거 기준(문서·절)을 함께 적는다. 코드 냄새는 "냄새 이름 → 리팩터링 기법"으로 적는다(예: 반복되는 switch → 조건부 로직을 다형성으로 바꾸기, 데이터 뭉치 → 매개변수 객체 만들기)
- 동작 불변 보장 전략 또는 동작 변경이 있을 경우 명시
- 리팩토링 우선순위 (아래 기준 참고)

### 우선순위 기준

등급의 틀만 정한다. 각 항목이 위반인지는 §2 기준 문서로 판정한다.

| 등급 | 해당 항목 |
|------|-----------|
| **Critical** | SSOT 위반(중복 정의된 상태·사실·규칙), 신뢰 경계의 계약 검증 누락, Fail-Fast 누락(silent ignore·암묵적 fallback) |
| **High** | convention Code Size 상한 초과, 계층·모듈 경계 혼재(구조 슬롯·의존 방향 위반), 사이드이펙트 미분리, 신호표 기본 심각도가 High인 냄새 |
| **Medium** | 그 밖의 코드 냄새, 네이밍, 주석(convention Comment Rules 기준 누락·과다·형식 불일치) |
| **Low** | import 정렬, 로깅 방식 정리(convention Logging 기준), 미사용 코드·import 제거 |

> 사용자 승인 없이 코드를 변경하지 않는다.

## 4. 실행

우선순위 순서(Critical → High → Medium → Low)로 진행한다. 각 항목은 계획에 적은 근거 기준대로 고치고,
기준 문서가 정한 패턴(계약 검증 헬퍼·에러 처리·주석 형식 등)을 그대로 쓴다.

- **이유를 알기 전엔 지우지 않는다(Chesterton's Fence)** — 이상해 보이는 분기·가드·우회 코드를 삭제·단순화하기 전에 `git log -L`/`git blame`으로 들어온 커밋 메시지를, grep으로 호출부를 확인한다. 존재 이유가 확인되지 않으면 지우지 말고 계획에 "의도 불명 — 확인 필요"로 남긴다.
- **변경 하나, 검증 하나** — 항목 하나를 바꿀 때마다 관련 테스트(없으면 린트·타입 체크)를 돌리고, 실패하면 그 변경만 되돌린 뒤 원인을 파악한다. 여러 항목을 몰아서 바꾼 뒤 한 번에 검증하면 어느 변경이 동작을 바꿨는지 가를 수 없다.
- **분할은 책임 기준으로** — 크기 상한을 넘는 파일·함수는 변경 이유가 다른 부분끼리 나눈다(판정: agent-principles [Structure] "File = what changes together"). 줄 수를 맞추려고 헬퍼를 쪼개지 않는다.
- **기계적 대량 변경은 도구로** — 같은 패턴을 수십 곳 이상 바꿔야 하면 손 편집 대신 codemod·`ast-grep`(preset의 "구조 패턴 일괄 치환" 절)·IDE 리네임을 쓰고, dry-run 결과를 계획 승인 때 함께 보여준다.

## 5. 검증 및 마무리

### 5-1. 동작 불변 검증 (테스트)

- 대상에 기존 테스트가 있으면 `devoks-sdlc:test-run-triage`(또는 대상 파일만 좁혀 직접 실행)로 리팩토링 전후 회귀 여부를 확인한다.
- 대상에 테스트가 없거나 커버리지가 낮으면, 이번 리팩토링을 되돌아볼 안전망이 없다는 뜻이므로 `devoks-sdlc:test-author`로 테스트 보강을 사용자에게 제안한다(적용 여부는 사용자 결정).

### 5-2. 린트 검증

- 프로젝트의 린트 스크립트(예: `npm run lint`, `pnpm lint`, `ruff check`)(Bash)로 수정한 파일 린트 확인, 오류 수정. Complexity Gate가 있으면 리팩토링 후 새 위반이 없는지도 여기서 확인한다.

### 5-3. 포맷 검증

- 프로젝트의 포맷 스크립트(예: `npm run format`, `pnpm format`, `biome format --write .`)(Bash)가 있으면 수정한 파일에 실행해 포맷을 맞춘다. 변경 파일 범위로 한정 실행 가능하면 그렇게 한다(전체 재포맷팅으로 인한 불필요한 diff 방지).
- 스크립트가 없는 프로젝트면 이 항목을 생략하고, 마무리 안내에 "포맷 스크립트 없음"을 명시한다(침묵 생략 금지).

- 미사용 import 최종 정리
- 리팩토링 요약 및 잔여 작업(추후 분리 필요 항목, 건너뛴 기준 문서) 안내

## Rules

- **기준은 참조만**: 위반 판정 기준은 §2 기준 문서가 SSOT. 이 절차에서 값·패턴을 새로 정하지 않는다
- **승인 우선**: 계획 수립 후 반드시 사용자 승인 받은 뒤 코드 변경
- **동작 불변**: 외부 동작 변경은 리팩토링 범위 밖. 변경 시 반드시 명시
- **Commit 조건**: 프로젝트가 실행 가능한 상태일 때만 커밋. Conventional Commits 형식, 한국어 메시지

## 실행 예시

**유저 입력:**

```
대상: src/features/order/
목표: 파일 크기 감축, Fail-Fast 적용
제약: 공개 API 시그니처 변경 금지
```

**실행 순서:**

1. `src/features/order/` 읽기 + 직접 의존 모듈 최소 탐색, 테스트·린트 기준선 확인
2. 위반 항목 도출(근거 기준 병기): `order.service.ts` Code Size 상한 초과(convention Code Size), 결제 응답 계약 검증 누락(convention 계약 검증 패턴), 실패 시 빈 배열 반환(agent-principles Explicit Handling), 주문 상태별 `switch` 3곳 반복(code-review Code Smells)
3. 계획: 변경 이유별로 파일 분할, 계약 검증 추가, 빈 배열 fallback → 명시적 에러, 상태 분기 → lookup 테이블 + 망라성 검사 → 사용자 승인
4. Critical → High → Medium → Low 순으로 실행(변경마다 검증)
5. 테스트·린트·포맷 확인, 요약 안내
