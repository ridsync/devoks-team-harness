## 1. 왜 와이어프레임 다음에 비주얼 단계가 있나

와이어프레임은 구조·흐름·정보 우선순위를 정할 뿐 **그대로 UI가 되지 않는다.** 와이어프레임에서 바로 디자인 시스템으로 넘어가면
정돈됐지만 밋밋한 화면이 나온다 — 특히 유입·첫인상·전환을 맡는 화면(랜딩·결과 미리보기·공유)은 비주얼이 지표를 좌우한다.
비주얼 단계는 레이아웃 변주·이미지/일러스트 스타일·색을 쓰는 방식·브랜드 모티프·모션을 정하고, 그 결과를 디자인 시스템 B-n의 입력으로 넘긴다.

| 단계 | 정하는 것 | 산출물 |
|---|---|---|
| 와이어프레임 (`phase=wireframe`) | 화면 구성·흐름·정보 우선순위·상태·비주얼 비중 | `WIREFRAMES.md` |
| 비주얼 (`phase=visual`) | 모티프·에셋 출처·색 사용·레이아웃 변주·인터랙티브 요소·모션 원칙, 강조 화면 하이파이 | `VISUAL.md` |
| 디자인 시스템 B-n | 비주얼 기준값을 토큰·컴포넌트·모션 계약으로 | `DESIGN.md` |
| 구현 | 하이파이 화면 + DESIGN.md 기준 | 코드 |

비주얼 단계는 **선택**이다. 강조 화면이 없는 제품(사내 도구·관리 화면 위주)은 건너뛰고 디자인 시스템 B-n으로 간다.

## 2. 결정 시점

| 항목 | 언제 | 이유 |
|---|---|---|
| 브랜드 모티프 | **시안 전** | 로고·일러스트·애니메이션·공유물이 모두 이것을 따른다 |
| 이미지 에셋 출처 | **시안 전** | 비용·라이선스·제작 기간·팀 규모가 달라진다 |
| 인터랙티브 요소 채택 | **시안 전** (§5 분류) | 일부는 기능(FR)이라 PRD·일정에 영향 |
| 레이아웃 변주 | 시안에서 | 보고 고르는 게 빠르다 |
| 색 사용·타이포 성격 | 시안에서 | 방향 시안 비교로 정한다 |
| 모션·마이크로 인터랙션 | 원칙은 시안에서 → 명세는 B-n | 성능 NFR·모션 줄이기 설정을 지켜야 한다 |

- 시안 전 결정에는 **되돌리는 조건**을 함께 적는다(예: "일러스트로 시작 — 브랜드 리뉴얼 시 재검토"). 에셋 결정은 나중에 바꿀 수 있지만 바꾸는 비용을 알고 정한다.
- 모티프는 제품 이름·핵심 가치·핵심 경험에서 출발해 **적용 지점**(로고·진행 표시·결과 시각화·공유 카드·모션)까지 같이 제안한다 — 적용 지점이 없는 모티프는 장식이다.
- 에셋 출처 비교 축: 브랜드 일관성 · 라이선스 · 비용 · 제작 기간 · 위험(AI 생성 인물의 어색함, 스톡의 흔함). 추천과 이유를 붙인다.

## 3. 입력 점검과 대상 화면 선정

| 상황 | HITL | 비-HITL |
|---|---|---|
| `WIREFRAMES.md` 없음 | 멈추고 와이어프레임 단계를 제안한다 — 동의하면 `phase=wireframe`으로 바로 이어서 진행 | 쓰지 않고 중단·보고 |
| TRD 없음 | 진행한다. 모션 구현 수단은 stack preset 기본값(없으면 `미확정`)으로 두고 §9에 올린다 | 같음 |
| WIREFRAMES 플랫폼 전제가 미확정 | 결정 라운드 **첫 항목**으로 다시 확인한다 | 가정으로 쓰고 blocker에 포함 |
| WIREFRAMES 미작도(`tool=none`) | 하이파이는 WIREFRAMES §4 문서 구조(우선순위 블록·문구)를 기준으로 그린다 — lo-fi 작도를 먼저 할 필요는 없다 | 같음 |
| 비주얼 비중이 없는 구버전 WIREFRAMES | 대상 화면을 제안하고 보고에 "WIREFRAMES 갱신 필요(patch — 비주얼 비중 기록)" | 같음 |

- WIREFRAMES §4의 **비주얼 비중 "강조"** 화면만 하이파이로 그린다(보통 2~4개 세트). 비중이 없으면 유입·첫인상·전환·공유를 맡는 화면을 PRD 지표·가정과 연결해 제안한다. 그런 화면이 하나도 없으면(관리 도구 위주) 비주얼 단계를 **건너뛰자고 제안**한다 — 진행 여부는 사용자가 정한다.
- 나머지 화면은 디자인 시스템을 일관 적용한다 — 전 화면 하이파이는 하지 않는다(검토되지 않고, 디자인 시스템과 이중 SSOT가 된다).

## 4. 진행 — 3라운드

1. **결정 라운드 (한 메시지)**: ① 대상 화면과 이유, ② 브랜드 모티프 제안(적용 지점 포함, 1~2안), ③ 에셋 출처 선택지와 추천, ④ 인터랙티브 요소 후보 표(분류·효과·추천), ⑤ 방향 시안 2~3개의 콘셉트 한 줄씩(추천 표시), ⑥ 도구 사전 조건(`design/visual.pen`을 새로 만들거나 열어 두기), ⑦ 사실 질문 — 기존 브랜드 자산(로고·색·사진)·제품명 확정 여부(와이어프레임과 달리 비주얼 단계에서는 브랜드가 범위 안이다). 플랫폼 전제가 미확정이면 그것이 ①보다 앞선다. 결정 항목은 번호로 묻고 추천을 붙인다 — 사용자는 번호별로 답한다.
2. **방향 시안 라운드**: 결정을 반영해 **같은 대표 화면 1개**를 방향마다 그려 나란히 놓고(프레임 `VD-A <방향>` …) 선택받는다. 방향마다 레이아웃 원칙·색 사용·타이포 성격이 달라야 비교가 된다.
3. **하이파이 라운드**: 선택한 방향으로 대상 화면 전체를 그린다(프레임 `HF W-n <화면>`). 기본 상태는 전부, 핵심 상태(잠금·결과 등)는 흐름상 결정적인 것만. 끝나면 §7 기준값을 추출한다.

- 화면 구조를 바꾸고 싶어지면 여기서 바꾸지 않는다 — WIREFRAMES 갱신(구조) → 비주얼 반영 순서.
- **비-HITL**: 결정은 제안값(`proposed`)으로 쓰고, 그릴 수 있으면 방향 시안까지만 그린다. 방향 선택과 하이파이는 하지 않는다 — 보고 첫머리에 "방향 선택 필요 — 하이파이·디자인 시스템 B-n 보류"를 blocker로 남긴다. 시안에서 정할 항목(VD-3~5)은 추천 방향 기준 제안값으로 쓰고 "시안에서 확정"을 붙인다.
- **미작도**(`tool=none`·도구 불가): §3 프레임 열은 "미작도", §6은 예정 프레임만, §7은 "미정 — 시안 후"로 둔다(방향별 후보값은 `후보`로 적을 수 있다). 보고에 이유와 재실행 방법(`tool=pencil`)을 남긴다.

## 5. 인터랙티브 요소 분류

두 축으로 나눈다 — **분류는 성격, 채택은 결정**이다.

| 분류 (성격) | 판정 기준 | 처리 |
|---|---|---|
| **기능 — FR 후보** | 새 데이터·상태·서버 호출·측정 대상이 생긴다 (예: 랜딩에서 1문항 바로 체험, 실시간 지표) | 채택·보류면 §8에 PRD FR 후보로 적고 보고에 "PRD 갱신 필요". PRD를 고치지 않는다 |
| **디자인 영역** | 표현만 바뀐다 (스크롤 등장, 숫자 카운트업, 결과 미리보기 예시) | 모션 원칙(§6)과 디자인 시스템 B-n으로 |

| 채택 (결정) | 기준 | 적을 것 |
|---|---|---|
| **채택** | 효과가 지표·가정과 연결되고 지금 비용이 감당된다 | — |
| **보류 — 출시 후** | 효과는 있으나 지금은 역효과·비용이 크다 (예: 초기 수치가 작은 사회적 증거) | 보류 이유와 **확장 지점**(레이아웃에 자리를 남길지, 데이터 수집을 미리 할지) — 나중에 넣을 때 재설계가 없도록 |
| **기각** | PRD Non-goals·Out of Scope와 충돌하거나 §6 모션 원칙 위반(장식 루프 등) | 기각 이유(충돌 대상 ID) |

- 비-HITL이면 채택 열 값에 `(제안)`을 붙인다.

- 후보마다 기대 효과를 PRD 지표·가정(A-n)과 연결한다. 연결이 없으면 장식이다.
- 추천은 분류와 함께 낸다(예: "A·B·D·E 채택, C는 출시 후 — 확장 지점: 히어로 하단 지표 슬롯").

## 6. 모션 원칙

- 모션은 **진행 피드백·상태 전환·의미 있는 순간**(잠금 해제, 결과 공개)에만 쓴다. 장식 루프·읽기를 방해하는 움직임은 쓰지 않는다.
- 모션 줄이기(웹 `prefers-reduced-motion`, 모바일 OS 설정)에서는 즉시 전환으로 대체한다.
- 성능 NFR(로딩·프레임)이 있으면 연결한다. 구현 수단은 TRD·preset을 따른다(react-web: `motion/react`, react-native: Reanimated). duration·easing의 토큰화는 디자인 시스템 B-n 몫이다.

## 7. 디자인 시스템 B-n으로 넘기는 것

- 시안이 **실제로 쓴 값**을 역할별로 적는다: 색(배경·표면·포인트·데이터), 타이포(서체 후보·크기 단계), 간격·반경·그림자, 모션(duration·easing·사용처), 일러스트·아이콘 규칙.
- 토큰 이름·계층·다크 모드 대응·컴포넌트 API는 쓰지 않는다 — DESIGN.md가 정한다.
- WIREFRAMES §5 컴포넌트 후보 중 강조 화면에만 쓰는 변형(예: 히어로 카드)을 표시한다.
- 보고에서 "디자인 시스템 B-n 착수 가능 — 입력: WIREFRAMES §5 + VISUAL §7"을 알린다.

## 8. PRD·TRD 영향

- PRD: 기능으로 분류된 인터랙티브 요소(FR 후보), 비주얼이 기대는 가정(A-n) 갱신.
- TRD: 비주얼 단계 채택(ADR), 에셋 정책(출처·라이선스·제작 도구), 모션 원칙(구현 수단·성능). TRD §2.1 디자인 도구 행이 바뀌면 함께.
- 둘 다 직접 고치지 않는다 — "PRD 갱신 필요 / TRD 갱신 필요(<무엇>)"로 보고한다.

## 9. 자체 점검 체크리스트

- [ ] 대상 화면이 강조 화면으로 한정되고 각각 이유(지표·가정)가 있다.
- [ ] 모티프·에셋 출처에 대안·이유·되돌리는 조건이 있다. 모티프에 적용 지점이 있다.
- [ ] 모든 인터랙티브 요소에 분류(기능/디자인 영역)와 채택 결정(채택/보류/기각)이 있고, 기능 채택·보류는 §8 FR 후보로, 보류는 확장 지점과, 기각은 이유와 함께 있다.
- [ ] 방향 시안이 2~3개이고 같은 대표 화면으로 비교됐다(HITL) / 비-HITL이면 하이파이 없이 blocker 보고.
- [ ] 하이파이 프레임이 §6과 1:1이다(그렸을 때).
- [ ] §7에 기준값만 있고 토큰 이름·컴포넌트 API가 없다.
- [ ] 모션 원칙에 모션 줄이기 대응과 성능 연결이 있다.
- [ ] WIREFRAMES의 화면 구조를 바꾸지 않았다(바꿔야 하면 WIREFRAMES 갱신 필요로 보고).

## 10. 갱신

- 디자인 변경(리브랜딩·에셋 정책 변경)은 VISUAL.md를 갱신한다 — 바뀐 결정은 지우지 않고 상태를 `superseded`로 두고 새 VD-n을 추가한다.
- WIREFRAMES 버전이 `wireframes_version`보다 높으면 영향받는 하이파이 화면을 "재작업 필요"로 보고한다.
- bump: major = 모티프·방향 교체 / minor = 화면·인터랙티브 요소 추가·변경 / patch = 정정.
- 이미 DESIGN.md가 있으면 §7 변경분을 "디자인 시스템 B-n 재검토 필요"로 보고한다.
