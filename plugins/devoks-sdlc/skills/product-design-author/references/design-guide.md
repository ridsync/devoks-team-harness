## 2. 범위 제안 — 한 메시지 확인 규칙

- 의도는 PRD가 이미 정했으므로 인터뷰하지 않는다. 화면 범위·충실도·흐름은 **판단**이라 제안하고 한 번에 확인받는다.
- 한 메시지에 담는 것 (순서대로): ① **플랫폼 전제**(아래), ② 화면 인벤토리 초안(W-n·목적·F-n), ③ 그릴 핵심 흐름(S-n), ④ 충실도(예: lo-fi 회색조), ⑤ 도구 사전 조건(Pencil이면 에디터에서 새로 만들거나 열어 둘 `.pen` 경로), ⑥ 이번에 다루지 않을 화면과 이유.
- **플랫폼 전제를 맨 앞에 둔다** — 화면 수·내비게이션 구조·레이아웃이 전부 여기서 갈리므로 뷰포트 숫자 하나로 다루지 않는다. 담을 것: 주 타깃 플랫폼(네이티브 앱 / 모바일 웹 / 데스크톱 웹 / 반응형), 사용자 역할별 기기(예: 회원 폰 · 원장 PC), 기준 뷰포트와 보조 뷰포트(예: 360×800 기준, 1280 보조).
  - TRD §2.1이 **확정**이면 인용만 하고 다시 묻지 않는다.
  - §2.1이 `제안`이거나 TRD가 없으면(PRD §7에서 가정) 이 메시지의 **첫 확인 항목**으로 묻는다. 플랫폼 전제가 확인되기 전에는 화면 인벤토리를 확정하지 않는다 — ②는 그 전제를 가정한 초안으로만 보여 준다.
  - 사용자가 플랫폼 전제를 바꾸면 그 전제로 다시 만든 인벤토리 **변경분만** 한 번 더 확인받는다 — 플랫폼이 바뀌면 화면 구성이 바뀌므로 한 메시지 원칙의 예외다.
  - 논의 결과가 TRD §2.1과 다르면 WIREFRAMES는 확인된 값으로 쓰고 보고에 "TRD §2.1 갱신 필요(<무엇이 어떻게>)"를 남긴다. 플랫폼 결정의 SSOT는 TRD이므로 이 스킬이 TRD를 고치지 않는다.
- 기본 범위: **MVP 기능의 사용자 접점 화면 + 핵심 시나리오 흐름**. 인벤토리·명세(§2·§4)는 화면이 있는 MVP F-n을 **모두** 덮는다. 그리기·검토는 한 차수에 보통 6~12개 — 넘으면 시나리오 단위로 차수를 나눠 §1 범위에 적는다(차수는 그리는 순서일 뿐 인벤토리를 줄이지 않는다). 한 번에 그린 30개 화면은 검토되지 않는다.
- 화면 구성에 영향을 주는 사실(기존 화면·법적 필수 문구·외부 연동 화면 등)이 입력에 없으면 묻는다. 답이 없으면 `미확정`. 브랜드 색·폰트·로고는 lo-fi 범위 밖이라 묻지 않는다(디자인 시스템 B-n 몫).
- PRD의 미결 질문(Q-n)이 화면 구성을 바꾸면(예: 원장이 PC도 쓰는가, 회원권 없을 때 예약을 막는가) 멈추지 않는다 — `미확정 (제안: <값>)`으로 가정해 같은 메시지에서 확인하고, 그 가정에 기댄 W-n을 §7에 연결한다. PRD를 직접 고치지 않는다.
- 비-HITL: 묻지 않는다. 제안 범위로 쓰고 보고에 확인 목록을 남긴다. 플랫폼 전제가 확정되지 않았으면 문서는 가정으로 쓰되 보고 첫머리에 "플랫폼 전제 미확정 — 확인 전 작도·FRD 착수 보류"를 blocker로 남긴다.

## 3. 화면 인벤토리 규칙

- **화면 = 사용자가 한 번에 보는 단위.** 모달·바텀시트는 별도 W-n으로 두되 진입 경로에 부모 화면을 적는다. 같은 화면의 상태(로딩·빈·오류)는 W-n을 늘리지 않고 §4 상태로 적는다.
- 모든 W-n은 F-n(또는 FR-n)과 S-n 중 하나 이상으로 역추적된다. 역추적이 없는 화면은 범위 밖이거나 PRD 누락이다 — 후자면 §6에 "PRD 갱신 필요"로 남긴다.
- 반대로 모든 MVP F-n 중 사용자 화면이 있는 것은 최소 하나의 W-n을 가진다(백엔드·알림 전용 F-n은 "화면 없음"으로 표시).
- 같은 화면을 다른 역할이 쓰면(예: 원장 대리 취소) W-n을 늘리지 않고 상태(`<역할> 모드`)로 적는다. 배치·주요 동작이 달라지면 별도 W-n.
- OS 권한 요청(알림·카메라·위치)은 화면 없는 F-n이라도 사용자 접점이다 — 처음 필요해지는 W-n의 상태로 적는다.
- 프레임 열은 디자인 파일의 프레임 이름(`W-n <화면>`)이다. 상태 프레임은 `W-n <화면> / <상태>`.

## 4. 화면별 명세 규칙

- **우선순위 블록**: 위에서 아래로 정보의 우선순위를 적는다. 핵심 문구는 실제 문장 초안으로 쓴다("Lorem ipsum" 금지 — 문구 길이가 배치를 바꾼다).
- **주요 동작은 하나.** 둘 이상이면 시나리오가 갈리는 신호다 — 사용 빈도가 높은 쪽을 주요, 나머지를 보조로 두고, 둘이 같은 무게면 화면을 나눈다. 판단이 안 서면 §7에 올린다.
- **상태**: 기본·로딩·빈·오류는 항상 검토하고, 해당 없으면 "해당 없음"으로 적는다. 게이트(로그인·결제·잠금·권한)·오프라인·부분 실패는 제품에 해당할 때 추가한다. FRD가 이 목록을 EARS AC로 옮긴다.
- **검증할 제약**: 화면으로 판정할 수 있는 NFR·리스크(글자 크기 하한·첫 화면 구성·터치 영역·한 손 조작 등)를 적고 §6에서 결과를 남긴다.
- 상태 프레임은 **기본 상태는 전 화면, 그 밖의 상태는 핵심 흐름 화면만** 그린다. 나머지는 §4 텍스트로 충분하다.

## 5. 컴포넌트 후보 → 디자인 시스템 B-n

- 올리는 기준: 두 화면 이상에서 쓰이거나, 한 화면이라도 변형·상태가 셋 이상인 것. 페이지 고유 레이아웃은 올리지 않는다.
- 이름은 역할로 짓는다(`QuestionCard`, `LockedPreview`) — 시각 속성(`BlueBox`)으로 짓지 않는다.
- TRD §2.1 컴포넌트 기반(예: shadcn/ui)에 이미 있는 것은 비고에 "기반 제공 — 래핑만", 없는 것은 "신규"로 표시한다. 기반이 완성 컴포넌트를 주지 않는 경우(스타일 엔진 + 자체 래퍼 — 예: NativeWind)는 전부 "신규"다. TRD §2.1이 없거나 컴포넌트 기반이 미정이면 "미정 — TRD §2.1 후 판정". 디자인 시스템 B-n의 공수가 여기서 갈린다.
- 이 스킬은 `FEATURES.md`를 고치지 않는다(기반 구역은 `product-trd-author` 소유). 디자인 시스템 B-n 시드의 "관련 문서"가 이 §5를 가리키므로, 보고에서 "디자인 시스템 B-n 착수 가능"만 알린다. B-n이 없으면 "TRD 갱신 필요 — 디자인 시스템 B-n 없음"으로, TRD 자체가 없으면 "TRD 작성 필요(`/devoks-sdlc:product-trd-author`) — §2.1 확정과 디자인 시스템 B-n 생성"으로 보고한다.

## 6. 와이어프레임 검증 (§6)

- 그린 뒤 §4 "검증할 제약"을 하나씩 판정한다: 충족 / 불충족 / 판단 불가(이유). 흐름에서 드러난 결정 공백은 결과를 `결정 필요`로 쓴다. 불충족이면 대안 배치를 제안하거나 PRD·TRD 영향으로 보고한다.
- 흐름에서 드러난 결정 공백(예: 잠금 범위, 가입 게이트 위치)은 PRD Q-n과 연결해 §6에 남긴다 — PRD를 직접 고치지 않는다.
- 도구로 그리지 못했으면(비-HITL·파일 미오픈) §6 결과는 "판단 불가 — 미작도"로 두고 보고에서 다음 HITL 실행을 안내한다. 텍스트만으로 "충족"이라 쓰지 않는다.

## 7. 자체 점검 체크리스트

- [ ] 모든 W-n이 F-n/FR-n·S-n으로 역추적되고, 화면이 있는 모든 MVP F-n에 W-n이 있다.
- [ ] 모든 핵심 시나리오(S-n)가 §3 흐름에 있고 게이트·이탈 지점이 노드로 보인다.
- [ ] 모든 W-n에 우선순위 블록·주요 동작 1개·상태(기본/로딩/빈/오류 검토)가 있다.
- [ ] §5 컴포넌트 후보가 기준(2화면 이상 또는 변형 3개 이상)을 따르고 역할 이름이다.
- [ ] 색·폰트·토큰 값·EARS AC·엔드포인트가 없다.
- [ ] `tool≠none`이면 디자인 파일 프레임이 §2 프레임 열과 1:1로 대응한다(어댑터의 대조 절차).
- [ ] §4 검증할 제약이 모두 §6에 결과로 있다(미작도면 "판단 불가 — 미작도").
- [ ] 모든 `미확정`·`제안`이 §7에 대응한다.

## 8. 갱신 모드

- 계기: PRD·TRD 버전이 frontmatter의 `prd_version`·`trd_version`보다 높거나, 화면 변경 요청.
- 변경 목록(W-n 추가/수정/삭제, 연쇄 영향: W-n → F-n FRD, 컴포넌트 후보 → 디자인 시스템 B-n)을 만들어 **확인 후** 쓴다. 비-HITL이면 보고만 한다.
- 삭제한 W-n은 지우지 않고 인벤토리에 `dropped`와 사유를 남긴다 — FRD가 참조한 화면 ID의 추적을 지키기 위해서다.
- 문서를 먼저 고치고 디자인 파일을 맞춘다(SSOT 순서).
- bump: major = 핵심 흐름·플랫폼 교체 / minor = 화면·상태·컴포넌트 후보 추가·변경 / patch = 문구·정정.
- 영향받는 FRD(FEATURES 상태 `frd` 이후)·디자인 시스템 B-n은 "재검토 필요"로 보고한다(직접 고치지 않는다).
